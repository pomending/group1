# 일정관리 데이터 명세

이 문서는 현재 `src/5_schedule` 구현을 설명한다. DB 테이블이나 API 명세가 아니며, 새 연동을 추가하지 않는다.

최종 반영 기준: 2026-10-29. 사용자 조작은 [일정관리 사용 안내](./SCHEDULE_USER_GUIDE.md)를 참고한다.

## 1. 데이터 흐름과 담당 파일

| 단계 | 담당 코드 | 처리 |
|---|---|---|
| 입력 기본값 | `scheduleData.js`의 `createEmptyForm` | 빈 폼 생성 |
| 수정 폼 | `createScheduleForm` | 저장 항목에서 입력 필드만 복사, 참석자를 문자열로 변환 |
| 기본 검증 | `validateScheduleForm` | 종류·분류·필수값·날짜·시간·반복 간격 확인 |
| 저장 준비 | `ScheduleManager.js`의 `addSchedule` | 이름 공백 정리, 참여자 검증, 충돌 확인, ID와 예외 정보 구성 |
| 상태·저장 | `scheduleHooks.js`의 `useScheduleStorage` | 변경된 목록 저장, 다른 탭 변경 병합, 충돌 시 저장 중지 |
| 불러오기 | `scheduleStorage.js`의 `loadSchedules` | 필수값 검사, 이전 형식과 누락값 보완 |
| 화면 계산 | `expandSchedules`, `getScheduleInterval` | 반복·여러 날 발생 항목 및 실제 시간 구간 생성 |

## 2. 브라우저 저장소

기존 외부 변경 지점은 `ScheduleManager.js`의 프로젝트 요약 갱신 effect다. `ERPContext.updateProject({ id, schedules })`를 호출하므로 프로젝트 저장뿐 아니라 Context의 프로젝트 변경 이력에도 영향을 준다. 5번 화면을 열거나 일정 내용이 달라져 요약이 불일치할 때 실행한다. 이 범위를 바꾸거나 다른 파트의 수정·삭제 기능을 추가할 때는 먼저 영향 범위를 설명하고 확인받는다.

값은 JSON 문자열이다. 브라우저와 사이트 주소가 같을 때 공유하며 사용자 계정별 서버 저장이 아니다.

| 키 | JSON 내용 | 용도 |
|---|---|---|
| `made-mate-schedules` | 일정 객체 배열 | 사용자가 등록한 원본 일정·반복 규칙·분리된 회차 |
| `made-mate-schedule-team` | 이름 문자열 배열 | 일정관리 내부 팀원 목록 |
| `made-mate-excluded-team` | 이름 문자열 배열 | 팀원 목록에서 제외한 이름 |
| `made-mate-schedules-backup-<시각>` | 정리 전 일정 JSON | 불러오기에서 손상·제외 항목 등을 발견한 경우의 백업 |

JSON 파싱이나 저장소 접근에 실패하면 원본 보호를 위해 자동 저장을 중지한다. 누락 필드 보완과 실제 사용자 입력 검증은 서로 다르다.

## 3. 저장 일정의 필드

아래 기본값은 새 폼과 새 저장 기준이다. 이전 자료는 불러오기에서 보완되며 일부 값은 유지된다.

### 식별·기본 정보

| 필드 | 저장 자료형 | 입력 조건·의미 | 기본값·보완 |
|---|---|---|---|
| `id` | string 또는 number | 일정 고유 식별자. 새 일정은 코드가 생성 | `schedule-<밀리초>-<난수>` 문자열. 기존 숫자 ID는 보존 |
| `title` | string | 일정명. 공백 제거 후 비어 있으면 저장 거부. 입력창 최대 80자 | 빈 폼은 `""` |
| `description` | string | 상세 메모. 입력창 최대 3,000자 | `""` |
| `scope` | string | `업무용`, `개인 일정용` 중 선택 필수 | 빈 폼은 `""`; 이전 자료의 잘못된 값은 `업무용` |
| `category` | string | 업무용 필수: `회의`, `프로젝트`, `업무`, `외근`, `휴가`, `기타` | 빈 폼은 `""`; 이전 자료는 기존 분류·참석자·프로젝트 정보로 추론 |
| `type` | string | 작업 색상 유형: `기획`, `디자인`, `제작`, `검수`, `마감`, `출고`, `기타` | `기획` |
| `status` | string | `pending`(예정), `completed`(완료) | `pending`; 개인일정 저장 시 `pending` |
| `visibility` | string | 공유 구분: `shared`(회사 공유), `private`(개인 표시) | `shared` |
| `isFavorite` | boolean | 즐겨찾기 여부 | 새 일정은 `false`; 일반 수정은 기존값 유지 |
| `color` | string | `typeColors`로 정한 카드 색상 | 기본 유형 색상. 직원·DB 관계 필드가 아님 |

개인일정에서는 업무 분류·상태 입력을 표시하지 않는다. 이전 저장 자료에 해당 필드가 존재할 수 있으므로 필드 존재 여부만으로 업무일정이라고 판단하지 않는다.

`visibility`는 표시·필터 구분이다. 현재 본인만 열람하도록 강제하는 인증·접근 제어는 없다. `scope`와 `visibility`는 별도 필드다.

화면에서는 `scope`를 **일정 종류**, `visibility`를 **공유 구분**으로 표시한다. 개인 일정용을 선택해도 공유 구분이 자동으로 개인 표시로 바뀌는 것은 아니다.

입력창의 `maxLength`와 저장 함수의 검증을 구분해야 한다. 모든 문자열 길이 제한이 불러오기나 외부 데이터에 동일하게 강제되는 것은 아니다.

### 프로젝트·담당자·참석자

| 필드 | 저장 자료형 | 조건·의미 | 기본값 |
|---|---|---|---|
| `project` | string | 프로젝트 표시 이름. 업무 분류가 `프로젝트`이면 필수 | `""` |
| `projectId` | string, number 또는 null | 선택적 기존 프로젝트 식별자. 개인일정·빈 프로젝트명·유효하지 않은 자료형은 null | `null` |
| `person` | string | 업무용 담당자 필수, 공백 정리 후 1~30자. 개인일정 저장 시 비움 | `""` |
| `attendees` | string[] | 회의 참석자. 빈 이름·중복 정리. 회의 이외 저장 시 빈 배열 | `[]` |

폼의 `attendees`는 쉼표로 연결한 문자열이고, 저장할 때 이름 배열로 변환한다. 참석자는 담당자와 별도다.

담당자·참석자는 이름 기반이며 직원 테이블의 FK가 아니다. 팀원 등록은 일정관리 내부 목록을 변경한다. 새 업무일정 저장 과정에서도 새 참여자 이름을 등록할 수 있다. 이미 제외된 이름은 관련 검증을 통과해야 한다.

`projectId`는 기존 코드에서 선택한 프로젝트를 찾아 저장한다. 이름만 입력한 프로젝트는 ID가 없을 수 있다. 이름을 입력한다고 다른 파트에 프로젝트를 신규 생성하지 않는다.

### 날짜·시간·알림

| 필드 | 저장 자료형 | 조건·의미 | 기본값 |
|---|---|---|---|
| `date` | string | 시작일 `YYYY-MM-DD`, 필수 | 새 폼 생성 시 오늘; 신규 등록창은 선택 날짜 사용 |
| `endDate` | string | 종료일 `YYYY-MM-DD` 또는 빈 문자열. 반복 없음일 때만 사용. 시작일 이상 | `""` |
| `time` | string | 시작 시간 `HH:mm` | `09:00` |
| `endTime` | string | 종료 시간 `HH:mm` | `17:00` |
| `isAllDay` | boolean | 종일 여부. 체크하면 시간 입력 숨김 | `false` |
| `reminderMinutes` | number | `0`, `10`, `30`, `1440`분 중 선택 | `0` |

- 종료일이 비어 있거나 시작일과 같으면 시간 지정 일정의 종료 시간은 시작 시간보다 늦어야 한다.
- 종료일이 뒤 날짜라면 첫날 18시~다음 날 9시도 허용한다.
- 종일이어도 시간 필드는 폼과 저장값에 남는다. 새 저장 검증은 이 값들의 시간 형식도 확인한다.
- 날짜·시각은 브라우저 현지 시간으로 계산한다. UTC 시각·시간대 필드는 별도로 저장하지 않는다.
- `getScheduleInterval`의 종료 경계는 제외한다. 종일 일정은 종료일 다음 날 00:00까지로 계산한다.
- 여러 날 일정은 연속된 한 기간이다. 달력에는 날짜마다 표시하고 다가오는 목록에는 한 번만 표시한다.
- 날짜별 카드 시간은 첫날 `18:00~24:00`, 마지막 날 `00:00~09:00`처럼 표시할 수 있다. `24:00`은 표시값이며 입력·저장 시간은 아니다.
- `getScheduleInterval(item)`은 실제 전체 기간을 반환한다. 충돌 검사는 `getScheduleInterval(item, true)`로 표시 날짜 안의 구간만 비교한다. 시작 전·진행 중 표시도 같은 전체 기간 계산을 사용한다.
- 알림은 앱이 열린 동안 화면에 표시한다. OS 푸시가 아니며 중복 방지 이력은 새로고침 시 초기화된다.

### 반복·회차 예외

| 필드 | 저장 자료형 | 조건·의미 | 기본값 |
|---|---|---|---|
| `repeatType` | string | `none`, `weekly`, `monthly` | `none` |
| `repeatInterval` | number | 반복 간격, 1~120 정수. weekly는 주, monthly는 개월 | `1` |
| `repeatEndType` | string | `none`(무제한), `until`(날짜), `count`(규칙 횟수) | `none` |
| `repeatEndDate` | string | until일 때 종료 기준일 `YYYY-MM-DD`. 시작일 이상 | `""` |
| `repeatCount` | number | count일 때 1~1000 정수 | `1` |
| `monthlyRule` | string | `date`(같은 날짜), `weekday`(몇째 주 요일) | `date` |
| `monthlyOrdinal` | number | `1`, `2`, `3`, `4`, `-1`(마지막) | `2` |
| `monthlyWeekday` | number | 0=일요일~6=토요일. 입력 UI는 월~금 제공 | `3`(수요일) |
| `holidayRule` | string | `keep`, `skip`, `nextWorkday` | `keep` |
| `excludedDates` | string[] | 반복 원본에서 제외한 규칙상 발생일 | `[]` |
| `replacesScheduleId` | string 또는 number 또는 빈 문자열 | 한 회차 수정·상태 변경으로 생성한 일반 일정이 가리키는 원본 ID | `""` |
| `replacesOccurrenceDate` | string | 분리된 일반 일정의 규칙상 원래 발생일 | `""` |

- 반복 규칙은 원본 한 건으로 저장한다. 월을 이동해도 실제 저장 건수가 늘지 않는다.
- 둘째 수요일은 `monthlyRule=weekday`, `monthlyOrdinal=2`, `monthlyWeekday=3`이다.
- `skip`은 주말·공휴일 회차를 표시하지 않는다. `nextWorkday`는 최대 14일 탐색하며 근무일을 못 찾으면 표시하지 않는다.
- 다음 근무일로 이동해도 제외·수정 기준은 이동 전 원래 발생일이다.
- 한 회차 수정은 원본의 `excludedDates`에 날짜를 추가하고 새 ID의 `none` 일정을 만든다. 원본 즐겨찾기를 새 회차에 복제하지 않는다.
- 한 회차 삭제는 원본에서 그 발생일을 제외한다. 전체 삭제는 원본 항목을 제거한다. 이미 분리된 일반 일정은 별도 저장 항목이므로 원본 삭제와 함께 자동 삭제된다고 가정하지 않는다.
- `monthly*` 필드는 월간 반복에서만 의미가 있다. 다른 반복 종류에 필드가 남아 있어도 규칙 계산에는 사용하지 않는다.
- 종료 조건은 이동 전 규칙 날짜·순번을 기준으로 계산한다. 휴일 건너뛰기와 삭제 회차도 횟수에 포함한다. 휴일 이동된 표시 날짜는 종료 기준일을 넘을 수 있다.
- 종료 옵션이 없는 기존 자료는 무제한으로 보완한다. 반복 없음·분리된 회차는 종료 조건을 none으로 정리한다. 과거 호환 필드 `repeatUntil`과 새 `repeatEndDate`는 다른 필드다.

## 4. 화면 계산 전용 필드

다음 값은 폼의 기본 입력 필드가 아니다. 원본 반복 규칙·실제 기간과 화면의 표시 날짜를 구분하는 데 사용한다.

| 필드 | 용도 |
|---|---|
| `occurrenceDate` | 반복 규칙상 원래 발생일. `date`는 휴일 규칙 적용 후 표시일일 수 있음 |
| `multiDayOccurrence` | 여러 날 일정의 시작일 이후 표시 항목 여부 |
| `originalStartDate` | 날짜별 표시 항목이 가리키는 실제 시작일 |
| `isProjectMilestone` | 프로젝트에서 계산한 읽기 전용 시작·마감 표시 |
| `milestoneType` | 프로젝트 날짜의 `시작일` 또는 `마감일` |
| `projectManager` | 읽기 전용 프로젝트 항목의 담당자 표시 이름 |

프로젝트 시작·마감 항목은 `ScheduleProjectBridge.js`에서 계산한다. 사용자가 등록한 `made-mate-schedules` 항목과 구분하며 수정·삭제·즐겨찾기를 제공하지 않는다.

## 5. 이전 자료 호환

- 기존 숫자 ID와 문자열 ID를 보존한다. DB 정수 ID로 변환하지 않는다.
- 누락된 종료 시간·공개 구분·참석자·반복 옵션 등에 기본값을 적용한다.
- 이전 `in_progress` 상태는 `pending`으로 읽는다.
- 이전 `biweekly`는 2주 간격으로 읽을 수 있다. `seriesId` 반복 자료는 그룹별로 정리한다.
- 정리한 자료에서는 `repeatUntil`, `seriesId`, `biweekly`, 과거 고객 연결 `connections`를 제거한다.
- 잘못된 필수값을 가진 일정은 표시 대상에서 제외될 수 있으며, 제외·손상 감지 시 정리 전 JSON을 백업한다.

## 6. 화면 상태 — 일정 객체에 저장하지 않음

시간 빠른 설정의 `durationMinutes`는 입력 이벤트용 이름이며 일정 필드가 아니다. `getScheduleDurationFields`가 계산한 `endDate`·`endTime`만 폼에 반영한다. 저장할 때 제목과 상세 내용의 앞뒤 공백을 정리하고 중간 줄바꿈은 유지한다.

`deletionNotice`는 삭제 전 원본(`before`), 한 회차 삭제 직후 원본(`after`, 전체 삭제는 null), 안내 문구, 만료 시각을 메모리에 보관한다. 15초 만료·닫기·새로고침 시 없어지며 다음 확정 삭제가 교체한다. `restoreDeletedSchedule`은 기존 ID나 변경된 반복 원본을 덮어쓰지 않는다. 복원은 기존 `setItems`·저장 훅을 거쳐 다른 탭 충돌 검사와 저장 상태 표시를 유지한다.

### 팝업과 작성 중 입력

- `ScheduleFormModal`의 `form`은 편집 중 입력이다. 일정 저장 전에는 원본 목록의 변경으로 취급하지 않는다.
- 최초 폼 JSON을 `initialFormRef`에 보관한다. 현재 폼과 다르면 취소·닫기·배경 클릭·Esc에서 폐기 확인을 표시한다. 원래 값으로 돌아오면 확인하지 않는다.
- 저장·삭제는 부모의 처리 결과로 닫는다. 전체 목록에는 입력 폐기 확인을 적용하지 않는다.
- 공통 `ScheduleModal`은 최초 초점·Tab/Shift+Tab 순환·Esc 닫기·닫은 뒤 초점 복귀를 처리한다. 접힌 설정의 입력과 비활성 요소는 초점 대상에서 제외한다.
- 브라우저 탭 닫기·새로고침·다른 페이지 이동 전체를 보호하는 `beforeunload` 기능은 아니다.

### 일정 저장 상태

`useScheduleStorage`의 `saveStatus`는 아래 값이며 일정 객체나 저장소에 기록하지 않는다.

| 값 | 화면 문구 | 판정 |
|---|---|---|
| `saving` | 저장 중… | 최초 처리 또는 저장 작업·잠금 대기 |
| `saved` | 브라우저에 저장 완료 | 일정 목록의 `localStorage.setItem` 성공 |
| `error` | 저장 실패 · 아래 안내를 확인하세요 | 일정 저장소 쓰기·저장 잠금 요청 등 실패 |
| `blocked` | 저장 중지 · 아래 안내를 확인하세요 | 최초 읽기 오류 또는 저장 충돌 |

저장 상태는 저장 대상 **일정 목록** 기준이다. 폼의 미제출 입력, 팀원 저장, 서버나 다른 기기의 저장 완료까지 보장하지 않는다. 팀원 저장 실패는 별도 경고로 안내한다. 최초 불러오기 이후 자동 기록에서도 완료가 표시될 수 있다.

## 7. 일정 복사·목록 정렬

- `createScheduleCopyForm`은 폼 필드만 복사한다. 이름에 ` (복사)`를 붙이고 80자 이내로 맞춘다. 상태는 pending으로 초기화한다.
- 복사본은 저장 전에는 원본 목록에 추가되지 않는다. 저장 시 새 ID·빈 제외일·즐겨찾기 해제 상태를 사용한다. 반복 원본 복사는 규칙과 종료 옵션만 유지하고 제외 회차는 복제하지 않는다.
- 날짜별로 선택한 한 회차를 복사하면 반복 없는 해당 날짜 일정으로 열린다. 여러 날 일정의 중간 날짜에서 복사하면 실제 시작일·종료일을 유지한다.
- `ScheduleListModal`의 `sortOrder`는 날짜·이름·담당자 표시 정렬 상태다. 저장하지 않으며 원본 배열을 변경하지 않는다. 담당자가 빈 항목은 담당자순에서 뒤로 보낸다.

## 8. 향후 DB 설계 시 결정할 사항 — 현재 미구현

| 항목 | 결정 필요 사항 |
|---|---|
| 기본키 | 기존 문자열 ID 유지 여부와 서버 ID 전환 방법 |
| 프로젝트 | 선택적 FK, 프로젝트 삭제·이름 변경 시 처리 |
| 사용자 권한 | 일정 소유자, 회사 범위, 서버의 접근 권한 검사 |
| 담당자·참석자 | 이름을 직원 ID로 연결할지, 참석자 관계 테이블을 둘지 |
| 반복 | 반복 규칙과 제외일·분리 회차를 어떻게 보존할지 |
| 시간대 | 현지 날짜·시간과 UTC 변환, 회사 기준 시간대 |
| 다중 사용자 저장 | 동시 수정 버전과 서버 충돌 정책 |

이 항목들은 설계 검토용이며 다른 파트의 테이블·Context·API를 변경하거나 연동하는 지시가 아니다.


## 9. 입력 안내·임시 보관·상태 필터

- getScheduleFormError는 첫 입력 오류의 field와 message를 반환한다. 기존 validateScheduleForm은 같은 검증 결과에서 문자열만 반환하므로 저장 검증 조건을 유지한다.
- ScheduleFormModal은 앱 검증 및 브라우저 invalid 이벤트를 관련 입력칸과 오류 문구에 연결한다. 추가 설정 안에 오류가 있으면 해당 details를 연다.
- useScheduleDraft는 새 일정 폼의 알려진 필드만 sessionStorage의 made-mate-schedule-draft에 version 1 형식으로 보관한다. 일정 원본 저장 형식은 변경하지 않는다. 기존 일정 수정은 제외하며 손상된 임시 자료는 명시적인 초기화 전까지 덮어쓰지 않는다.
- 목록 statusFilter는 팝업 내부 상태다. 전체는 개인·업무를 유지하고 예정·완료는 업무만 필터링한다. 반복 분리 회차의 관계 계산은 필터 전 전체 목록을 사용한다.
