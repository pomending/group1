## 1. 종합 판단

**핵심 업무의 정상 흐름은 상당 부분 안정화되었고, 현재도 내부 리허설은 가능하다. 다만 상담 저장의 부분 반영과 몇 가지 화면 연동 누락을 정리한 뒤 최종 발표 시연에 사용하는 것을 권장한다.**

이번 통합본에서는 고객·견적·상담 삭제 보호, 견적 가격 계산 통일, 기본 단가 보존, Project/Task 참조 검증의 Context 이동이 확인됐다. 특히 이전에 가능했던 작업 종류 변경을 통한 배송 완료 우회는 훅의 종류 변경 금지로 막혔다. 정상 배송 완료·선행 작업 미완료 시 거절·완료 후 프로젝트/작업 잠금·변경 이력·저장 복원도 실행 검증을 통과했다.

새로 확인한 주요 연동 문제는 **대시보드 프로젝트 바로가기의 상세 선택 누락**, **일정 참석자 참조가 남은 직원 삭제**, **퇴사 영업 직원을 신규 상담 담당자로 선택 가능**이다. 이미 알려진 상담 저장 순서와 메모 중복 문제는 현재 소스에도 남아 있으며 React 화면 조작 테스트로 재현했다.

## 4. 구조와 검증 책임

### 4.1 모듈 배치

`1_crm` 고객, `2_quotation` 견적, `3_projects` 프로젝트, `4_tasks` 작업, `5_schedule` 일정, `6_dashboard` 대시보드/공지/커뮤니티/프로필, `7_login` 인증 화면, `8_hr` 직원/계정, `9_consultation` 상담, `10_product` 상품, `11_homepage` 외부 고객 홈페이지로 구성된다. `context`, `utils`, `data`가 공통 상태·검증·초기값을 담당한다.

홈페이지는 외부 고객용 화면이라는 설정을 기준으로 평가했다. 내부 ERP와 같은 코드에 있다는 이유로 내부 업무 권한을 홈페이지에 일괄 적용하도록 권장하지 않는다. 홈페이지 상품 조회는 공통 상품 배열을 읽고 판매 중 상품만 표시한다. 클레임은 아직 별도 흐름이다.

### 4.2 Provider 래퍼가 실제 사용되는가?

`src/context/ERPContext.js:972–1003`에서 원본 훅들을 먼저 spread하고, **그 뒤** 아래 래퍼를 같은 이름으로 다시 지정한다.

- `deleteConsultations`, `deleteCustomers`
- `updateEmployee`, `deleteEmployee`
- `addQuotation`, `updateQuotation`, `deleteQuotation`
- 프로젝트 CRUD 및 작업 CRUD

따라서 화면에서 `useERP()`로 받는 함수는 통합 래퍼다. 이 덮어쓰기는 의도된 것이며 spread 순서 때문에 원본 함수로 되돌아가는 문제는 확인되지 않았다. `completeProject`는 28행에서 분리해 공개하지 않는다. 훅 간 무관한 동일 함수명 충돌도 발견하지 못했다.

예외적으로 고객 `addCustomer/saveEditedCustomer`, 상담 `addConsultation/updateConsultation`, 여러 setter/reset 함수는 별도 통합 참조 래퍼 없이 공개된다. 관련 위험은 F07/F09에 정리한다.

## 5. 핵심 업무 흐름 실행 결과

### 5.1 프로젝트 자동 완료

1. 일반 TaskDetail 수정은 Context `updateTask:836`으로 들어간다.
2. 변경 전 소속 프로젝트 존재·미완료와 작업 참조 조건을 검사한다.
3. 배송이 미완료→완료로 전환되면 `canCompleteProject`가 제작·검수·포장 각각의 존재 및 `progress==='완료'`를 검사한다.
4. 선행 조건 통과 후 작업 훅이 작업 자체 값과 변경 불가 필드를 검사한다.
5. 작업 수정 성공 때만 내부 `completeProject`를 호출한다.
6. 프로젝트 상태 완료, 완료일, 상태/완료일 두 필드가 들어간 변경 이력 한 건이 만들어진다.

**실행 확인**: 선행 미완료 또는 잘못된 마감일 요청은 프로젝트·작업·이력을 유지했다. 정상 요청은 작업과 프로젝트가 함께 완료되고 진행률 100%, 재마운트 뒤 완료 상태/이력 유지였다. 실제 TaskDetail DOM에서도 먼저 배송 완료 거절→제작 완료→배송 완료→등록 폼/수정 버튼/관리 열 사라짐→기존 네 작업 조회 유지가 통과했다.

제작·검수·포장 사이의 세부 선후 순서를 강제하는 코드는 없다. 이번 사용자 명세에서 명시적으로 보장해야 하는 조건은 **배송 완료 전 세 작업 모두 완료**이므로 앞 세 단계에 별도 순서가 없다는 사실만으로 오류 판정하지 않았다. 팀이 추가로 원하면 정책을 따로 합의해야 한다.

### 5.2 삭제 보호

- 고객: 상담·견적·프로젝트 참조와 자동 등록을 검사한 뒤 전체 삭제. 하나라도 잘못된/참조 대상이면 전체 취소 확인.
- 상담: 견적 요청 상태이거나 mock claims의 consultationId가 참조하면 삭제 거절. 다중 삭제도 변경 전에 검사.
- 견적: 프로젝트 연결이면 수정/상태 변경/삭제 금지. 승인 완료 단독 견적도 삭제 금지.
- 직원: 프로젝트·작업·견적·고객·상담·계정 참조면 삭제 거절. 일정 담당자 정리 후 삭제하지만 **일정 참석자 참조는 누락**(F05).
- 프로젝트: 완료 또는 작업 존재 시 삭제 금지. 작업 없는 프로젝트 삭제는 저장 일정 연쇄 정리 성공 때만 진행.
- 상품: 현재 공개 API/관리 UI에 `deleteProduct` 기능이 없다. 판매중지 방식이므로 존재하지 않는 삭제 기능을 오류로 평가하지 않았다. 직접 `setProducts`로 목록을 줄이는 우회 가능성은 F09와 같은 위험이다.

### 5.3 직원 변경과 계정

진행 프로젝트 담당자 또는 미완료 작업 담당자가 자격을 잃는 휴직/퇴사/부서 변경은 Context에서 막는다. 완료 작업 담당자를 그대로 두는 예외는 유지된다. 일반 직원 퇴사는 연결 계정을 비활성화하고 현재 세션을 로그아웃시킨다. 마지막 활성 ADMIN을 퇴사시켜 계정을 비활성화해야 하는 요청은 직원 상태 변경 전에 거절하는 것을 실행 확인했다.

견적의 기존 직원은 계속 참조할 수 있고 새 선택은 영업팀 재직자로 제한한다. 다만 고객/상담 새 담당자 선택은 부서만 확인하므로 HR에서 퇴사시킨 영업 직원을 새 상담에 넣을 수 있다(F04).

### 5.4 견적 가격 및 상태

- 생성 시 기본 단가를 숫자로 저장하고 `options:[]` 또는 `{name,unitPrice}` 배열을 저장한다.
- 새 상품 선택은 상품 기본 가격과 일치해야 하며, 기존 동일 상품 유지 시 기본 단가 직접 변경은 거절한다.
- 상품 가격 변경·판매중지 뒤에도 기존 견적 수량 변경은 가능하고 기본 단가는 보존된다.
- 기본 8,000 + 옵션 500 + 300 = 최종 단가 8,800 계산, 빈 옵션/할인/유효하지 않은 옵션 검사가 통과했다.
- 승인 대기→승인/반려, 승인/반려→재검토(승인 대기) 버튼 경로는 정상 구조다. 프로젝트 연결 견적은 재검토도 거절한다.
- **미연결 승인/반려 견적의 내용 변경 제한은 화면만 존재**한다(F06). 일반 상세 수정 버튼은 숨겨져 있으므로 기본 클릭만으로 내용이 바뀌는 문제로 분류하지 않는다.
- 일부 숫자/상태/날짜 검증은 현재 직접 잘못 호출하면 통과한다(F07). 구버전 호환 문제와는 무관하다.

### 5.5 일정·대시보드·홈페이지

일정은 Context의 프로젝트·직원·작업을 받아 프로젝트 시작/마감과 작업 마감을 읽기 전용 마일스톤으로 만든다. 저장 일정과 복제하지 않는다. 프로젝트 이름·직원 이름/상태 불일치는 브리지 경고로 안내한다. 기본 삭제 연계와 기존 일정 테스트는 통과했으나 참석자 삭제 참조가 남는 문제는 신규 발견이다.

대시보드 최근 프로젝트 목록은 같은 projects를 읽고 완료 프로젝트를 제외한다. 오늘 일정은 일정 저장소와 프로젝트 마일스톤을 계산하며 storage/focus/visibility/timer로 갱신한다. 목록의 내용 연계는 있으나 프로젝트명 버튼이 넘긴 `openProjectId`를 대상 화면이 소비하지 않는다(F03).

홈페이지 상품은 공통 products와 상품 이미지 저장값을 읽는다. 클레임의 공통 claims/consultationId 연계는 D01로 분리했다.

## 6. 문제 상세 — ① 정상 화면 조작에서도 발생하는 오류

각 파일 경로는 ZIP 루트의 `src/` 기준이며 줄 번호는 원본에서 1부터 센다. DOM 재현은 실제 브라우저 시각 검사가 아닌 React 화면 테스트다.

### F01 · 높음 · 상담 저장 실패 뒤 고객이 먼저 생성/변경됨

- **파일/함수**: `src/9_consultation/02_ConsultationManagement.js:44–158` `saveConsultation`, 특히 89–130행과 135–140행. 거절 규칙은 `src/context/useConsultationData.js:105–146` `updateConsultation`.
- **분류**: ① 정상 화면 오류. 이미 알려졌던 문제의 **현재 미해결 확인**.
- **발생 조건**: 견적 요청 상담을 상세로 연 뒤 고객사명을 기존에 없는 이름으로 바꿔 저장. 화면은 수정 가능하지만 상담 훅은 원래 customerId 변경을 금지한다.
- **재현**: 초기 데이터에서 견적 요청 상담 체크→상세보기→고객사명 `검수 신규고객` 입력→등록/수정 저장.
- **기대**: 상담 제약 검사에서 거절되면 고객과 상담 모두 바뀌지 않아야 한다.
- **실제**: “견적 요청된 상담의 고객은 변경할 수 없습니다.” 경고, 상담은 원본 유지, 고객은 **50→51개** 증가. UI02 통과로 재현했다.
- **모듈 영향**: 불필요한 autosave 고객이 남고 삭제 정책에도 걸릴 수 있다. 다른 기존 고객명으로 바꾼 경우 해당 고객 연락처/메모가 먼저 변경되는 위험도 같은 순서에서 보인다(이 변형은 정적 확인).
- **최소 수정**: 기존 상담 상태/customerId 불변 검사를 고객 CRUD 전에 수행. 검증 함수로 최종 상담·고객 변경안을 먼저 만들고 성공 가능한 경우에만 변경한다. 현재 단계에 DB 트랜잭션 도입은 불필요하다.
- **발표 전**: **반드시 해결 권장**. 오류 알림 뒤 데이터가 늘어나는 경로이므로 시연 신뢰도에 직접 영향.

### F02 · 보통 · 같은 상담 저장 때 고객 메모가 반복 추가됨

- **파일/함수**: `src/9_consultation/02_ConsultationManagement.js:111–128` `saveConsultation`.
- **분류**: ① 정상 화면 오류. 알려진 문제의 **현재 미해결 확인**.
- **조건/재현**: 기존 고객에 연결된 견적 요청 상담 상세를 열고 아무것도 바꾸지 않은 채 저장. 같은 상담을 다시 열어 또 저장.
- **기대**: 새 메모/상담 내용 변경이 없다면 고객 메모 유지.
- **실제**: 날짜+같은 메모가 다시 붙는다. UI01에서 첫 저장 후 50자, 두 번째 후 82자. `existingCustomer.memo !== editData.updatedMemo`는 계산한 `updatedMemo` 변수 대신 존재하지 않는 필드를 비교한다.
- **모듈 영향**: CRM 메모 증가, 이력으로 오인, 1,000자 입력 제한과 별도로 누적 길이 증가 가능.
- **최소 수정**: 오타만 고쳐도 새 문자열은 매번 달라지므로 충분하지 않다. 기존 상담 memo와 편집 memo를 비교해 실제 변경 때만 추가하거나, 동일 상담의 동일 내용이 이미 반영됐는지 간단히 검사한다.
- **발표 전**: **반드시 해결 권장**. 반복 저장만으로 재현된다.

### F03 · 보통 · 대시보드 프로젝트명이 해당 상세를 열지 못함

- **파일/함수**: `src/6_dashboard/DashboardPage.js:145–149` 프로젝트 버튼; `src/3_projects/ProjectPage.js:10–30` 초기 page/selectedProjectId.
- **분류**: ① 정상 화면 오류, **이번 추가 발견**.
- **조건/재현**: 대시보드 최근 프로젝트명을 클릭.
- **기대**: 클릭한 ID의 프로젝트 상세 또는 명확한 프로젝트 링크 동작.
- **실제**: navigate는 `{state:{openProjectId:project.id}}`를 보내지만 ProjectPage는 useLocation/state를 읽지 않고 `page='list'`로 시작한다. UI03에서 목록 heading과 보기 버튼들이 나오고 상세 페이지는 없음 확인.
- **모듈 영향**: 대시보드→프로젝트 상세 연계가 끊긴다. 데이터 손실은 없다.
- **최소 수정**: ProjectPage에서 전달된 ID 존재를 검사하고 selectedProjectId/page를 detail로 설정. 전체 라우터 재설계 없이 해결 가능하다.
- **발표 전**: 해당 버튼을 시연한다면 **수정 권장**. 링크가 목록 이동 목적이라면 전달 state와 문구를 정리해 의도를 일치시킨다.

### F04 · 보통 · 퇴사 영업 직원을 신규 상담 담당자로 지정 가능

- **파일/함수**: `src/9_consultation/02_ConsultationManagement.js:260–277` 담당자 select 및 `saveConsultation:44–158`; `src/context/useConsultationData.js:73–101` `addConsultation`.
- **관련 화면**: 고객 등록 `src/1_crm/03_CustomerRegister.js:163–175`, 고객 수정 `03_CustomerEdit.js:145–158`도 부서만 필터(정적 확인).
- **분류**: ① 정상 화면 오류/정책 불일치, **이번 추가 발견**.
- **조건/재현**: 프로젝트·미완료 작업을 맡지 않은 영업 직원을 HR에서 퇴사 처리→신규 상담에 해당 직원 선택→처리 중으로 저장.
- **기대**: 신규 직원 선택은 재직·해당 부서 조건 적용. 기존 완료 기록 담당자 유지와 구분.
- **실제**: UI06에서 일반 `updateEmployee` 퇴사 성공 후에도 직원이 선택지에 있고 신규 상담 employeeId로 저장됨. 선택 숫자 타입은 정상이다.
- **모듈 영향**: HR 퇴사 상태와 신규 담당 업무가 불일치. 견적 단계에서 같은 직원을 새로 고르면 거절되어 모듈 정책이 달라진다.
- **최소 수정**: 신규 선택은 재직 영업 필터, 저장 함수에서도 직원 존재·재직·부서를 확인. 기존 담당자를 유지해야 한다면 원본과 동일할 때만 별도 예외 옵션을 둔다.
- **발표 전**: 상태 변경을 포함하는 발표라면 **해결 권장**. 고객/상담의 신규 배정도 재직자 정책이라는 전제로 판정했다. 팀이 별도 정책을 의도했다면 명시할 필요가 있다.

### F05 · 보통 · 직원 삭제 후 일정 참석자의 FK가 남음

- **파일/함수**: `src/context/ERPContext.js:278–334` `deleteEmployee`; `src/5_schedule/scheduleStorage.js:264–309` `deleteSchedulesByEmployee`, 특히 285–287행.
- **분류**: ① 정상 기능 조합에서 발생하는 참조 오류. **실행 증거는 Context+현재 형식 일정 fixture**이며 브라우저에서 일정 등록부터 끝까지 클릭한 것은 아니다.
- **조건**: 다른 ERP 데이터/계정 참조가 없는 직원이 일정의 주담당자가 아니라 `attendeeEmployees`에만 등록됨.
- **재현**: 신규 직원 등록→업무 일정 참석자로 지정→직원 삭제. 자동 테스트는 신규 직원 CRUD 후 현재 일정 형식의 숫자 attendee ID를 준비해 삭제했다.
- **기대**: 참조 중이면 삭제 금지, 또는 참석자 연결을 명시적으로 정리하는 정책.
- **실제**: 삭제 `ok:true`, 직원 사라짐, 일정 `attendeeEmployees[0].id` 유지. 통합 T26 재현. 함수는 item.employeeId만 검사한다.
- **모듈 영향**: 일정에 없는 직원 참조가 남는다. 브리지의 “직원 정보가 없습니다” 경고가 표시될 수 있으므로 즉시 화면 충돌과는 다르다.
- **최소 수정**: 참석자 참조도 삭제 전에 검사해 거절하는 방식이 가장 간단하다. 이름만 남기는 정책을 택하면 attendeeEmployees 정리와 안내가 필요하다.
- **발표 전**: 직원 삭제·일정 연계를 시연한다면 **수정 권장**. 주담당자 일정 삭제는 기존대로 동작한다.

## 7. 문제 상세 — ② 잘못된 함수 호출·예외 상황의 잠재적 위험

### F06 · 보통 · 미연결 승인 완료/반려 견적 내용 변경이 저장 함수에서 허용됨

- **파일/함수**: `src/context/ERPContext.js:444–491` `updateQuotation`; `src/context/useQuotationData.js:83–125`; 화면 `src/2_quotation/QuotationDetail.js:104–119,320–330`.
- **조건**: 프로젝트 미연결 견적이 승인 완료/반려인데 Context에 quantity/memo 등 내용 변경을 직접 전달. 일반 상세 화면은 수정 버튼을 숨긴다.
- **기대**: 내용 변경은 거절, 허용된 재검토 상태 변경만 가능.
- **실제**: T16에서 승인 완료 후 quantity 321 저장 성공, 반려 후 memo 변경 성공. 프로젝트 연결 견적은 정상적으로 거절된다.
- **영향**: 이전 화면/다른 호출부/편집 중 상태 변화에서 승인 내용이 바뀔 수 있다. 현재 기본 상세 버튼만 눌러 수정되는 문제로 확대하지 않는다.
- **최소 수정**: 원본 상태가 승인 완료/반려면 바뀐 필드를 검사해 내용 변경을 막고 허용된 상태 전환만 처리한다.
- **발표 전**: **가능하면 수정**. 이미 알려진 미해결이며 정상 버튼 경로의 우선순위는 F01/F02보다 낮다.

### F07 · 보통 · 고객/상담 원본 CRUD와 견적의 값 검증이 일부 누락됨

- **파일/함수**: `src/context/useCustomerData.js:24–55` `addCustomer/saveEditedCustomer`; `src/context/useConsultationData.js:73–146`; `src/utils/quotationUtils.js:32–130` `validateQuotation`.
- **조건/현재 호출 재현**:
  - `addCustomer({companyName:'테스트',employeeId:'999'})` → 현재 문자열 FK 저장(T25).
  - `addConsultation({companyName:'테스트',customerId:999,employeeId:999})` → 없는 숫자 FK 저장(T25).
  - 정상 참조를 가진 견적에 `quantity:'2'`, 상태 `없는상태`, `2026-99-99/2027-99-99` 날짜 → 저장 성공(T17).
- **기대**: 저장 경계에서 타입·존재·상태 목록·실제 날짜를 검증/정규화.
- **실제**: 견적 FK는 최근 Context 검증으로 문자열/없는 참조가 차단됐다. 그러나 quantity는 Number로 검사만 하고 원본 문자열을 저장하며 상태 목록/실제 날짜는 검사하지 않는다. 고객/상담은 화면의 필드 검사 의존이 크다.
- **영향**: 후속 표시·검색·담당자 참조 오류 가능. **마이그레이션이나 과거 문자열 ID 문제는 아니다.**
- **최소 수정**: 기존 유틸을 저장 함수에서도 사용하고 허용 필드만 저장. 숫자는 검증한 최종 숫자값을 저장하고 dateUtils의 isValidDate를 재사용.
- **발표 전**: **가능하면 수정**. 정상 화면은 대체로 숫자로 변환하므로 UI 오류와 구분한다.

### F08 · 보통 · 퇴사 직원 로그인/세션 복원 방어가 인증 훅에는 없음

- **파일/함수**: `src/context/useAuthData.js:19–28,31–58,69–75`.

### D01 · 홈페이지 클레임의 공통 배열/상담 연계

- 파일: `src/context/ERPContext.js:15,982`, `src/data/mockData.js:1598–1613`, `src/11_homepage/HomeInquiry.js:18–61,81` 이후.

### D02 · 일정 자체 ID는 숫자 통일 정책의 예외가 남음

- 파일: `src/5_schedule/ScheduleManager.js:50–51,522`; `ScheduleProjectBridge.js:92` 부근 및 작업 마일스톤 ID.
- 저장 일정 신규 ID를 `schedule-시간-랜덤` 문자열로 만든다. 프로젝트/작업 가상 마일스톤도 화면용 문자열 ID가 있다.
- 이는 **과거 문자열 ID 호환 문제가 아니라 현재 생성 코드의 실제 형식**이다. 현재 일정 내부는 문자열 ID를 전제로 동작하며 관련 기존 테스트도 통과했다. 값 때문에 즉시 참조가 깨졌다는 증거는 없다.
- **판정: 숫자 PK 통일 적용이 아직 끝나지 않은 범위/정책 차이**. 일정의 프로젝트·직원 FK와 일정 자체 ID, 화면용 가상 ID를 구분해야 한다.
- 최소 방향: “모든 PK” 정책에 저장 일정이 포함된다면 신규 저장 일정 ID만 숫자로 바꾸고 중복/연속 등록/다중 탭 충돌을 재검증한다. 가상 마일스톤 UI key까지 억지로 숫자로 바꿀 필요는 없다. 발표 직전에 일괄 치환하는 것은 권장하지 않는다.

## 9. ④ 선택적 구조 개선

### S01 · Context 길이와 검증 함수 정리

`ERPContext.js`가 약 1,015행이지만 현재 래퍼 공개 순서는 올바르다. 발표 전에 대규모 분리보다 이미 있는 validateQuotationReferences/validateProjectReferences/validateTaskReferences를 유지하고, 상담 사전 검증만 작은 공통 함수로 추출하는 편이 안전하다. 타입 변환 비교를 일괄 정리하는 작업은 기능 수정을 마친 뒤 진행해도 된다.

### S02 · 다중 상태 변경과 저장 보장의 한계

프로젝트·작업은 React state 변경 뒤 각각 effect로 저장하며 이력/next ID는 별도 쓰기다. 성공 반환이 디스크 영속성이나 다중 탭 원자성을 보장하지 않는다. 이번 일반 완료/실패 테스트에서는 상태가 맞았지만 모든 쓰기 실패 시점을 전수 검증하지 않았다. 현재 팀 수준에서는 실패 결과 통일·예외 안내·중복 클릭 방지가 우선이며 새로운 상태 라이브러리나 트랜잭션 시스템 도입은 필요하지 않다.

### S03 · 개발용 접근 설정과 전체 초기화 안내

`src/App.js:27`의 REQUIRE_LOGIN=false는 개발/시연 설정으로 남아 있다. 계정 관리 라우트는 ADMIN 검사, 공지 작성은 역할 검사가 있다. 이 설정을 실서비스 보안 결함으로 확대하지 않는다. 발표에서 로그인 차단을 보여주려면 설정을 미리 맞춰 리허설해야 한다.

전체 초기화는 ERP 각 도메인과 저장 일정 본문을 초기화하고 로그아웃한다. 공지/커뮤니티/프로필/홈페이지 문의/일정 팀원 저장값까지 같은 범위인지 안내 문구를 정리하면 좋다.

## 11. 수행하지 못한 검사와 한계

- 실제 Chromium 실행은 환경의 `socket() ... Operation not permitted`로 중단됐다. 별도 원격 브라우저에서도 검수용 localhost 접속이 거절되어 주요 업무 흐름을 실제 브라우저로 완료하지 못했다. 이 제약은 ERP 앱 오류 판정이 아니다.
- 실제 페이지 새로고침은 미검증이다. React 재마운트로 localStorage/sessionStorage를 다시 읽는 복원은 실행 확인했다.
- 실제 고객 등록/수정 popup의 window.opener 수명, 팝업 차단, 부모 창 이동/닫힘은 미검증. 일반 팝업이 열리는 환경에서 수동 확인이 필요하다.
- 이미지 업로드·엑셀 다운로드 파일 열기·인쇄·모바일 CSS·브라우저별 키보드 접근성은 전수 미검증.
- 공휴일 API 실제 응답, 장시간 알림/날짜 변경, 복수 탭 동시 변경 전체 조합은 미검증.
- 일정 참석자 참조 재현은 현재 형식 일정 fixture를 사용했다. 일정 UI 신규 작성부터 직원 삭제까지 실제 브라우저 클릭한 결과는 아니다.
- 모든 저장 effect와 이력 next ID 쓰기의 실패 시점은 전수 검증하지 않았다. 상품 reset 실패·일정 읽기 실패만 별도 주입했다.
- 기존 단가 보존은 **동일 상품 유지** 범위를 확인했다. 상품을 다른 것으로 변경하면 새 상품 가격으로 바뀌는 현 구현은 최근 합의 방향으로 보았으며, “상품 변경도 금지” 정책인지는 추가 합의 사항이다.
- 구버전 localStorage 문자열 ID 및 마이그레이션은 요청에 따라 제외했다. 그 내용을 이번 오류 목록에 다시 올리지 않았다.
- Git 이력은 ZIP만으로 확인할 수 없어 담당자별 커밋/merge 충돌 이력은 검증하지 않았다. 현재 통합 결과를 기준으로 판단했다.
- 검사 중 오류/실패 suite가 있어도 나머지 검사는 계속 진행했다. 검수용 테스트의 “통과”는 재현 assertion 성공도 포함하므로 결함 0개를 뜻하지 않는다.

## 최종 안정성 평가

**핵심 업무 흐름의 안정성은 이전 통합본보다 개선되었다.** 프로젝트/작업 리팩터링에서 주요 검증이 사라졌다는 증거는 없었고, 참조 삭제·가격 계산·자동 완료 잠금의 정상 경로는 실제 실행으로 확인됐다. 현재 가장 우선할 것은 새 아키텍처 도입이 아니라 **상담 저장의 부분 반영과 반복 메모, 대시보드 및 일정/직원 연동의 작은 누락을 고치는 작업**이다.

11월 20일 발표까지 8일을 기준으로, 위 우선순위 1–4와 실제 브라우저 리허설을 마치면 프론트엔드 포트폴리오 시연에 적합한 수준으로 준비할 수 있다. 현재도 검증된 정상 흐름의 내부 리허설은 가능하지만, 이 보고서가 실제 브라우저 전체 검증 또는 운영 서비스 수준의 안정성을 보장하는 것은 아니다.
