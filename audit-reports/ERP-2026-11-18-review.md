## 2. 확인된 수정 필요 사항

### R-01 [P2 / 실제 UI 동작 불일치] 마감 안내 출력 형식과 색상 조건 불일치

- **위치:** `src/utils/projectUtils.js` 약 33~60행; `src/3_projects/ProjectList.js` 약 28~46행.
- **원인:** `getDeadlineStatus()`는 `D - 3`, `D - Day`, `D + 2`처럼 공백을 포함해 반환한다. 하지만 `ProjectList.js`는 `deadline === "D-Day" || /^D-[1-3]$/.test(deadline)`을 주황색 임박 조건으로 사용한다.
- **영향:** 마감 임박 1~3일 및 당일 프로젝트에 `pm-deadline-soon`이 적용되지 않을 수 있다. 사용자가 요청한 공백 없는 `D-20`, `D-Day`, `D+2` 형식도 충족하지 않는다.
- **재현:** 날짜 유틸 직접 실행에서 마감 당일 실제 반환값 `D - Day`, 기대값 `D-Day`로 불일치.
- **제안:** `getDeadlineStatus`의 세 출력 지점을 각각 `D-${daysLeft}`, `D-Day`, `D+${Math.abs(daysLeft)}`로 바꾸고, 목록의 `/^D-[1-3]$/` 및 `D-Day` 분기를 유지한다. 완료 프로젝트의 `완료` 표시는 그대로 둔다. **이 변경은 실험용 풀스택 복사본에만 적용했으며, 공식 ZIP에는 적용하지 않았다.**

### R-02 [P2 / 검증 우회 위험] 공개 상담 CRUD와 통합 저장의 입력 검증 범위 차이

- **위치:** `src/context/ERPContext.js` `saveConsultationRecord()`(약 149행), `addConsultation()` / `updateConsultation()`(약 179~204행), `saveConsultationWithCustomer()`(약 207행).
- **관찰:** `saveConsultationWithCustomer()`는 `validateConsultationForm(editData)`를 수행하지만 `saveConsultationRecord()`는 담당 직원·고객 FK만 검증한다. 따라서 다른 컴포넌트에서 일반 `addConsultation()`/`updateConsultation()`을 직접 호출하면 필수 입력·전화번호·이메일 형식 검사를 통합 저장 경로와 똑같이 거치지 않는다.
- **영향:** 정상 화면에서는 통합 저장을 사용하더라도 Context API 사용자 또는 이후 새 UI 경로에서 검증 차이가 생길 수 있다.
- **제안:** 공통 저장 경계에 입력 검증을 배치하되 **신규 고객 자동 생성 전에 선검증**이 먼저 실행되도록 유지. Context만 변경해도 해당 경로는 보완 가능하나 추가 입력값 계약 검사를 동반해야 한다.
- **확인 수준:** 정적 코드 경로 분석. 의도하지 않은 CRUD 호출에 대한 React 런타임 재현은 못 함.

### R-03 [P2 / 구조적 위험 · 기존 보류] 다중 상태 저장 실패 시 부분 반영

- **위치:** `src/context/ERPContext.js` `saveConsultationWithCustomer()` 약 380~408행, `updateTask()` 약 1699~1721행, `resetAllData()` 약 1822행 이후.
- **관찰:** 통합 상담 저장은 고객 생성 이후 상담 저장을 수행하며, 기존 고객 수정 경로는 상담 저장 이후 고객을 수정한다. Task 상태→프로젝트 상태/이력 갱신도 여러 React State 업데이트로 나뉜다. 전체 초기화는 다수 Hook과 브라우저 저장소 변경을 차례로 수행한다.
- **영향:** 중간 단계가 거부되거나 localStorage 기록에서 예외가 나면 전체를 하나의 DB 트랜잭션처럼 원복할 수 없다.
- **분류:** 이전에 이미 보류한 **B-01/전체 초기화 원자성**을 포함한 구조적 한계. React 발표 버전에서 무리하게 DB식 트랜잭션을 흉내 내기보다, 실패 시 안내·재시도·초기화 시연 통제 권장.
- **백엔드 실험:** 이전 풀스택본은 트랜잭션 방식이므로 별도 실험본에서 이 문제를 줄일 수 있는지 검증했다. MySQL 실기동은 이번 환경에서 못 함.

## 4. 모듈별 확인 내용과 미실행 항목

1. **고객·상담:** 존재하지 않는 고객 ID 검증·재직 영업 담당자 검사·인계 완료 제한 코드 확인. 미배정 상담 필터 구현 확인. 신규 고객 자동 생성/기존 고객 수정/중복 상담 경고 UI의 실제 상호작용은 미실행.
2. **견적·상품:** 상품 기본 단가와 견적 기준 단가 분리, 옵션 음수 허용, 안전 정수 수량 검사, 프로젝트에 연결된 견적 제한 코드 확인. 가격 계산·정식 등록/재검토/삭제 전체 상태 전이의 실제 화면 재현은 미실행.
3. **프로젝트·Task:** 승인 완료 견적 선별, 프로젝트 5개 카드, 세부 작업 4개 카드, master에서 온 읽기 전용 아코디언, 단계 드롭다운, 프로젝트 그룹별 페이지네이션 확인. 단계 마감일 순서와 선행 완료 규칙은 Context 코드·초기 데이터에서 확인, UI에서 각 수정 버튼을 눌러 확인하지는 못함.
4. **직원·계정·로그인:** 소스 존재와 import 무결성 확인. 휴직/퇴사 담당자 인계, 마지막 관리자, 로그인 회복·비활성 처리 전체 기능은 브라우저 테스트 필요.
5. **일정·대시보드:** 관련 소스 파싱/경로 검사 완료. 휴일·반복 일정·프로젝트 연동·일정 삭제·달력 전환 등 실제 일자별 테스트는 미실행.
6. **외부 홈페이지·클레임:** 최신 React에는 `HomeInquiry.js`와 `useClaimData.js` 기반의 클레임 기능 존재. 실제 고객 검증, 이미지 업로드, 권한/공개 범위, 서버 저장 여부는 이번 React 정적 검사만으로 보증 불가.
7. **CSS/UI:** 코드 파싱과 파일 존재 검사는 진행. 실제 폰트 렌더링, 반응형 레이아웃, 누적 CSS 우선순위 충돌은 브라우저 미실행이므로 확인 불가.
