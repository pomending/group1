# 공식 React ERP 발표 직전 최종 재검수

**2026년 11월 20일 · 조건부 발표 가능**

정상 저장값을 가진 발표용 브라우저에서 ERP 한 탭으로 시연할 수 있다. **P1-1과 P1-3은 해결**, **P1-2와 P1-4는 의도된 정책**이다. 기존 P1 중 미해결 항목은 0건이다. 최신 프로덕션 빌드에서도 서로 다른 탭의 프로젝트 저장 유실과 손상된 고객 저장값에 의한 로그인 화면 중단을 재현했다. **미해결 P0은 2건**이다.

## 3. P1-3 · 임시 견적 정식 등록 시 판매 상태

1. Chromium의 새 견적 화면에서 상담 #11, 판매 중인 스테인리스 텀블러, 영업 담당자, 수량 25와 거래 조건을 입력하고 임시저장했다.
2. 상품 관리에서 해당 상품을 판매중지로 바꿨다. 견적 목록 → 임시 저장 → 불러오기 → 견적서 저장을 누르자 **“판매중지된 상품은 정식 견적으로 등록할 수 없습니다.”**가 표시됐다.
3. 시도 직전과 직후의 저장된 견적 목록 전체와 상담 목록 전체를 비교했다. 두 목록 모두 동일했다. #16은 임시 저장, #11은 견적 요청 상태를 유지했다. Provider 테스트에서도 메모리 상태와 저장값을 대조했다.
4. 상품 관리에서 판매를 재개한 뒤 같은 임시 견적을 불러와 #15로 정식 등록했다. 견적·상담이 함께 갱신됐고 새로고침 후에도 유지됐다.
5. 별도 Provider 테스트에서 기본 단가 2,500원인 정식 견적 생성 후 상품 단가를 3,100원으로 바꾸고 판매를 중지했다. 기존 견적의 메모 수정은 성공했고 저장 단가는 2,500원이었다. 같은 상품의 견적 기본 단가를 3,100원으로 직접 덮어쓰는 수정은 거부됐다.

**코드 근거.** `src/context/ERPContext.js` 957–968행에서 임시 저장 → 승인 대기 전환 시 현재 판매 상태를 검사한다. 1201–1219행에서 참조 검증 → 견적 갱신 → 상담 인계 순으로 처리한다. `src/context/useQuotationData.js` 98–108행은 기존 상품을 유지할 때 보관 기본 단가의 변경을 거부한다.

## 4. 정책 판정 정정

**전체 데이터 초기화.** 개발·시연 환경에서는 모든 로그인 계정이 실행할 수 있다는 팀 정책과 일치한다. 발표 도중 확인하면 같은 브라우저의 업무 데이터와 계정 변경 상태까지 초기화된다. 운영 환경에 그대로 제공하면 일반 직원의 조작으로도 업무 자료를 잃을 수 있으므로 운영 전환 시 별도의 접근·복구 정책이 필요하다. 근거는 `src/components/Sidebar.js` 12–24행과 `src/context/ERPContext.js` 1861–1904행이다.

**프로젝트 마감일.** 견적 #10으로 프로젝트를 생성하자 납품일 2026-12-12가 초기 마감일로 복사됐다. 프로젝트 마감일을 2026-12-19로 변경해도 견적 납품일은 12월 12일이었다. 별도 미완료 프로젝트에서 마감일을 시작일로 당겨 기존 작업 마감일을 벗어나게 하자 ‘기존 세부 작업의 마감일이 프로젝트 기간을 벗어납니다.’가 반환됐고 프로젝트 배열은 그대로였다. `src/context/ERPContext.js` 1337–1344, 1385–1398행. 발표에서 기간을 조정해도 된다.

## 5. 추가로 확인한 견적 경계 사례

확인한 정상 시연 경로에서 두 수정으로 인한 회귀는 발견되지 않았다. 다음 두 현상은 최신판에서 실제로 재현했다. 이번 수정 전후로 동일한 절차를 비교한 자료가 없어 도입 시점은 확정할 수 없다.

| 항목·우선순위 | 재현과 영향 | 원인 및 수정 방향 |
|---|---|---|
| P2 · 임시 견적에서 상담 선택 해제 후 예전 번호가 남음 | Chromium에서 #11을 골라 임시저장 → 불러오기 → 상담을 빈 항목으로 변경 → 다시 임시저장. 견적 #17에 `customerId: null`, `consultationId: 11`이 함께 저장됐다. 새 견적 선택지에서 아직 ‘견적 요청’인 #11이 빠졌다. 실제 화면과 React DOM 양쪽에서 확인했다. 해당 임시 견적에서 다른 상담을 명시적으로 선택하거나 불필요한 임시 견적을 삭제하면 된다. | `QuotationCreate.js` 169행은 선택을 비워도 기존 상담 번호를 다시 사용한다. 54–63행은 그 번호가 다른 견적에 있으면 선택지에서 제외한다. 임시 견적의 명시적 해제를 저장할 때 고객·상담 ID를 함께 비우도록 한다. |
| P2 · Context 호출의 검증 대상과 저장 대상 불일치 | 정식 신규 생성과 임시 → 정식 전환을 각각 독립 실행했다. 견적 객체에는 #24, 인계 인수에는 #11, 고객에는 #11의 고객을 넣으면 두 호출 모두 성공했다. 기존 견적 #4와 신규 견적이 #24를 중복 참조하고 #11은 연결 견적 없이 인계 완료됐다. 일반 화면의 유효한 선택에서는 재현되지 않았다. 이전 보고서 P1-1의 보완 제안이 지적했던 별도 경로다. | `ERPContext.js` 1036–1085, 1174–1219행에서 검증·인계는 별도 인수, 저장은 견적 객체를 사용한다. 두 값의 일치를 저장 전에 확인하거나 하나의 ID로 검증·저장·인계한다. |

두 사례 모두 기존 정식 견적의 상담 교체 차단과 판매중지 상품의 정식 전환 차단 판정에는 영향을 주지 않는다.

## 6. 남은 P0 및 발표 주의사항

| 항목 | 최신 빌드에서의 재현 | 발표에서의 조치 |
|---|---|---|
| P0-1 여러 탭 저장 유실 | 같은 프로필에서 두 탭이 프로젝트 #1 ‘삼성전자 텀블러 제작’과 #2 ‘한국대학교 에코백 제작’의 수정 화면을 각각 열었다. A에서 #1 이름을 ‘검수 A’로 저장하고 저장소에 반영된 것을 확인했다. B에서 #2를 ‘검수 B’로 저장한 뒤 A를 새로고침하자 #1은 원래 이름, #2는 ‘검수 B’였다. `src/context/useProjectData.js` 15–38, 63–70행의 탭별 배열 로딩·전체 저장 구조에서 발생한다. | **같은 브라우저 프로필에서는 ERP 한 탭만 편집한다.** 다른 프로젝트를 선택해도 유실될 수 있다. |
| P0-2 손상된 고객 저장값 | 격리한 브라우저에서 `erp_customers`를 불완전한 JSON인 여는 중괄호 한 글자로 설정하고 로그인 화면을 열었다. 파싱 예외가 기록되고 앱 루트가 비었다. `src/context/useCustomerData.js` 9–19행에서 Provider 초기화 중 발생한다. 일반 입력만으로 손상이 생기는 경로는 이번 검수에서 확인되지 않았다. | **발표할 프로필에서 미리 로그인 화면과 새로고침을 확인한다.** 문제가 있는 프로필은 데이터를 보존하고, 발표는 깨끗한 별도 프로필에서 진행한다. |

발표 순서는 한 탭에서 **견적 요청 상담 선택 → 견적 저장·자동 인계 → 승인 → 프로젝트 생성 → 제작·검수·포장 완료 → 배송 완료**로 진행할 수 있다. 초기 상태라면 새 견적은 상담 #11, 프로젝트부터 시작하려면 승인 완료 견적 #10을 사용할 수 있다. 임시 견적의 상담을 바꿀 때는 새 상담을 직접 고른다. 전체 데이터 초기화는 시연 자료가 더 필요하지 않은 시점에만 사용한다.
