# 공식 React ERP 발표 직전 통합 검수
**2026년 11월 20일 · 굿즈 제작·판매 ERP · 최종 판정은 조건부 발표 가능**

## 발표팀이 먼저 볼 결론

| 질문 | 판단 |
|---|---|
| 오늘 발표할 수 있는가? | **가능하다.** 깨끗한 브라우저 프로필에서 ERP 한 탭으로 상담 인계, 견적 승인, 프로젝트 생성, 네 단계 작업과 배송 완료를 시연할 수 있다. 실제 프로덕션 화면에서 저장된 ID와 완료일을 확인했다. |
| 반드시 수정할 문제가 있는가? | **여러 탭에서 편집하는 시연은 P0-1 수정 전 진행하면 안 된다.** 같은 고객의 상담을 바꾸는 견적 수정과 판매중지 상품의 임시 견적 복원도 현재 규칙을 깨뜨린다. 아래 단일 탭 경로만 발표한다면 당일 코드 변경은 필수적이지 않다. 데이터 보존이나 권한 통제를 보장한다고 소개하려면 관련 P0·P1을 먼저 수정해야 한다. |
| 무엇을 피해야 하는가? | 한 브라우저 프로필에서는 한 탭만 편집한다. 발표 중 ‘전체 데이터 초기화’를 누르지 않는다. 승인 대기 견적의 상담을 다시 선택하거나 프로젝트 납기를 수정하지 않는다. 판매 상태가 바뀐 상품의 임시 견적은 사용하지 않는다. |
| 실제 결과는? | 설치 성공, 프로덕션 빌드 성공. 기존 Jest **11개 스위트 중 10개 통과, 453건 중 442건 통과·11건 실패**. 추가 Context 통합 시나리오 **8건 기대 결과 일치**. 이 중 3건은 결함 재현이다. 정상 시연 경로에서 미처리 JavaScript 예외 0건. 손상 데이터 주입 시에는 실제 흰 화면과 예외가 발생했다. |
| 무엇이 남았는가? | 발표 PC의 기존 저장값, Windows Edge, 실제 배포 서버의 직접 URL 새로고침 설정, 공휴일 API 성공 응답, 모든 화면의 모든 버튼 조합은 검증 불가. 초기 데이터와 한 탭 정상 경로의 통과가 여러 탭의 저장 안전성을 보장하지 않는다. |

## P0 — 치명적

### P0-1. 다른 프로젝트를 편집해도 먼저 저장한 탭의 변경이 사라진다

- **브라우저 재현.** 같은 프로필에서 로그인한 두 탭으로 프로젝트 화면을 연다. A에서 프로젝트 #12의 이름을 ‘탭A 변경’, 마감일을 12월 17일로 저장한다. B에서는 그 전에 열어 둔 ‘에이스모빌리티 전시회 티셔츠 제작’의 설명만 바꿔 저장한다. A를 새로고침하면 #12의 이름이 ‘검수 시연’, 마감일이 12월 15일로 돌아왔다. A의 첫 저장 직후에는 두 변경 모두 저장소에 있었다.
- **위치·원인.** `src/context/useProjectData.js:15`에서 탭별 초기 배열을 읽고, 같은 파일 63–70행에서 프로젝트·이력 배열 전체를 별도로 저장한다. 197–205행의 수정은 현재 탭 메모리를 기준으로 한다. 저장 직전 다른 탭의 버전을 검사하지 않는다.
- **영향.** 서로 다른 행을 수정해도 정상 저장된 업무 데이터가 유실된다. 확인된 대상은 프로젝트다. 같은 구조인 다른 모듈에서의 유실 범위는 별도 검증이 필요하다.
- **발표 판단·수정.** 한 탭만 편집하면 이 재현 조건을 피할 수 있다. 저장 시 최신 버전을 확인하고 변경이 있으면 거절·재조회하게 한다. 동시 쓰기를 지원하려면 읽기·검사·쓰기를 직렬화하고 프로젝트 및 이력을 함께 반영한다. ‘두 탭, 서로 다른 행’이 회귀 테스트에 포함되어야 한다.

### P0-2. 손상된 고객 저장값 하나로 로그인 화면까지 열리지 않는다

- **브라우저 재현.** 별도 테스트 프로필에서 고객 저장 키 `erp_customers`에 불완전한 JSON인 여는 중괄호 하나를 넣고 `/login`을 다시 열었다. `JSON.parse` 예외가 발생하고 앱 루트가 비었다. 일반 UI에서 이 손상값이 만들어지는 현상은 관찰하지 않았다.
- **위치·원인.** `src/context/useCustomerData.js:9–19`가 저장값을 예외 처리나 배열 형식 확인 없이 읽는다. `src/context/ERPContext.js:30`이 화면 선택 전에 훅을 실행하고 `src/App.js`의 `App`이 로그인 화면까지 같은 Provider로 감싼다.
- **영향·수정.** 해당 프로필에서는 ERP 초기화 버튼에도 접근할 수 없다. 손상값을 보존하면서 복구 안내를 표시하고, 복구 전 자동 덮어쓰기를 차단한다. 파싱 실패와 파싱은 되지만 배열이 아닌 경우를 모두 처리한다. 발표는 정상 로그인과 새로고침을 확인한 프로필에서 진행한다.

## P1 — 높음

### P1-1. 정식 견적 수정에서 같은 고객의 다른 상담을 선택하면 인계 관계가 깨진다

- **브라우저 재현.** 초기 견적 #4는 삼성전자, 승인 대기, 상담 #24에 연결돼 있다. 같은 고객에 대해 새 ‘견적 요청’ 상담을 등록한다. 검수에서는 #34였다. 견적 #4 상세 → 수정 → 새 상담 선택 → 견적서 저장을 실행했다.
- **실제 결과.** 견적 #4의 참조가 #24에서 #34로 바뀌었다. #24는 연결 견적 없이 ‘인계 완료’, #34는 정식 견적과 연결되고도 ‘견적 요청’이었다. 새 견적 화면은 이미 사용한 #34를 선택지에서 제외한다. 수정 화면에 처음 들어갔을 때 기존 인계 상담도 선택 상자에 표시되지 않았다.
- **위치·원인.** `src/2_quotation/QuotationCreate.js:54–63,165–170,224–231,358–374`는 견적 요청만 선택지로 만들고 수정 시 선택한 상담 ID를 저장한다. `src/context/ERPContext.js:1137–1198`는 정식 견적의 고객 변경은 검사하지만 상담 변경은 차단하지 않는다. 인계 처리는 임시 견적의 정식 전환 시에만 수행한다.
- **영향·수정.** 고객이 같아도 개별 문의의 처리 이력과 새 견적 대상이 틀어진다. 정식 견적 수정 화면에 원래 상담을 읽기 전용으로 표시하고 Context에서도 기존 `consultationId` 변경을 거부한다. 등록 시 검증할 상담 ID와 실제 저장할 ID도 하나로 통일한다. 발표에서는 새 견적을 생성한 뒤 상세 화면에서 승인한다.

### P1-2. 일반 직원도 전체 ERP 데이터를 초기화할 수 있다

- **브라우저 재현.** 일반 직원으로 로그인해 최초 비밀번호를 변경했다. 계정 관리 직접 접근은 정상적으로 인사 화면으로 돌아갔지만, 같은 계정의 사이드바에서 ‘전체 데이터 초기화’를 누르고 확인하자 로그아웃됐다. 프로젝트 12→11건, 견적 16→15건으로 돌아갔고 새로 만든 프로젝트가 사라졌다.
- **위치·원인.** `src/components/Sidebar.js:8–24,77–86`이 역할 조건 없이 버튼과 실행 함수를 제공한다. `src/context/ERPContext.js:1839–1873`의 초기화 진입점에도 관리자 검사가 없다.
- **영향·수정.** 해당 브라우저의 여러 계정이 공유하는 업무 데이터와 비밀번호 변경 상태까지 영향을 받는다. 확인 창은 있지만 일반 직원도 승인할 수 있다. 시연 편의 기능으로 유지한다면 관리자에게만 표시하고 함수 진입점에서도 역할을 확인한다. 발표 중에는 모든 계정에서 이 버튼을 피한다.

### P1-3. 판매중지 상품이 임시 견적에서 그대로 정식 등록된다

- **브라우저 재현.** 상담 #11과 판매 중인 스테인리스 텀블러로 견적을 임시저장한다. 상품 화면에서 해당 상품을 판매 중지한 뒤 견적 목록 → 임시 저장 → 불러오기 → 견적서 저장을 누른다. 판매중지 상태에서 견적 #16이 ‘승인 대기’로 등록됐다. Context 재현에서는 상담 ‘인계 완료’까지 확인했다.
- **위치·원인.** `src/context/ERPContext.js:944–974,1149–1198`에서 판매 상태 검사를 상품이 새로 선택된 경우에만 수행한다. 임시 → 정식 전환 때 상품 ID가 같으면 기존 상품으로 취급한다. 일반 신규 견적의 판매중지 상품 선택 차단은 정상이다.
- **영향·수정.** 정식 접수 시점에 판매할 수 없는 상품이 승인 절차로 들어간다. 정식 전환 순간에 상품의 현재 판매 상태를 다시 검사하고, 실패 시 상담 인계와 견적 갱신을 모두 중단한다. 기존 정식 견적의 보관 단가는 유지한다.

### P1-4. 프로젝트 수정에서 견적 납품일과 다른 마감일을 저장할 수 있다

- **브라우저 재현.** 견적 #16의 납품일 2026-12-15를 이어받은 프로젝트 #12의 수정 화면에서 마감일을 2026-12-17로 바꿨다. 프로젝트 저장이 성공했고 견적 납품일은 그대로였다. 다른 탭이 개입하기 전 단독 저장 시점에 확인했다.
- **위치·원인.** `src/3_projects/ProjectEdit.js:43–51,182–190`에서 마감일을 입력·전달한다. `src/context/ERPContext.js:1312–1320,1344–1385`는 생성 시 견적 기한을 복사하지만 수정 시에는 고객·견적 ID와 기존 작업의 기간 위반만 검사한다.
- **영향·판정 기준.** 이번 요청의 ‘프로젝트와 견적의 납품일 일치’를 수정 후에도 유지해야 하는 조건으로 판정했다. 현재 소스 주석은 **생성 시** 복사를 명시한다. 팀 의도가 내부 생산 마감일을 독립 운영하는 것이라면 두 날짜를 별도 항목으로 표시하고 그 정책을 설명하면 된다.
- **수정.** 일치가 필수라면 프로젝트 마감일을 읽기 전용으로 표시하고 Context에서 연결 견적의 `deliveryDate`와 다른 값을 거절한다. 발표 중 프로젝트명을 수정해도 되지만 마감일은 유지한다.

## 발표 동선과 남은 위험

발표용 프로필로 로그인하고 한 번 새로고침해 대시보드가 뜨는지 확인한다. 이어서 한 탭에서 **상담 #11 → 새 견적 저장 → 인계 완료 조회 → 견적 승인 → 프로젝트 생성 → 네 작업 등록 → 배송 선행 완료 거절 → 제작·검수·포장·배송 완료 → 새로고침 후 완료 상태 확인** 순으로 진행한다. 준비 과정에서 #11을 이미 썼다면 #15 또는 #19 등 현재 ‘견적 요청’ 목록에 남은 상담을 쓴다.

정상 경로에서는 미처리 JavaScript 예외가 없었지만 외부 폰트 CSS와 한국 공휴일 API 요청은 검수 환경에서 실패했다. 화면 렌더링과 개인 일정 저장은 계속 동작했다. 관련 위치는 `src/index.css:1`, `src/5_schedule/scheduleHooks.js:49–81`이다. 발표장 네트워크, 실제 공휴일 표시, 저장공간 소진, 브라우저별 파일 다운로드 및 장시간 다중 사용자 사용은 검증하지 못했다. 모든 모듈의 모든 조작을 실브라우저에서 반복한 것은 아니며, 위 표의 ‘Context’와 ‘기존 테스트’는 해당 계층에서 확인한 결과다.
