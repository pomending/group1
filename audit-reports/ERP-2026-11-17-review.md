## 1. 결론

**핵심 업무 흐름은 시연할 수 있는 수준이다. 다만 작업 목록의 수정 이벤트 1건은 발표 전에 고치거나 입력 기능을 제거해야 한다. 이 조치 없이 현재 ZIP을 최종 안정화 완료본으로 선언하기는 어렵다.**

프로덕션 빌드는 성공했다. 실제 ERPProvider를 사용한 통합 실행에서 고객 → 상담 → 견적 승인 → 프로젝트 생성, 작업 병행 진행 → 순차 완료 → 배송 완료 → 프로젝트 자동 완료 및 이력, 완료 후 잠금, 담당 고객 인계 후 휴직, 퇴사 시 계정 비활성화가 동작했다. Task 상세 관리 화면의 등록·수정·삭제도 실제 React 이벤트로 확인했다.

반면 `/tasks` 목록의 진행 상태·단계·담당자 select는 존재하지 않는 `setTasks`를 호출한다. 이것은 접기·펼치기 동작의 완성도 문제가 아니라 실제 데이터 수정 이벤트의 런타임 오류다. **팀원이 11월 18일 목록을 완성할 때 반드시 함께 확인할 통합 연결 문제**로 보고한다. 접힘 초기 상태·레이아웃·행 클릭 UX 자체는 판정하지 않았다.

초기 데이터의 핵심 PK/FK와 프로젝트·작업 상태/일정 정합성은 통과했다. 다만 견적 6번의 음수 할인 옵션은 현재 검증 함수가 거부한다. 견적 수량은 실제 화면에서 소수도 저장된다. 상담 FK 및 견적 상태의 중앙 검증 누락은 직접 Context 호출로 확인했으나, 일반 화면에서 임의 FK/상태를 선택하는 경로까지 재현한 것은 아니다.

- 신규 고객 → 견적 요청 상담 → 정식 견적 등록 → 상담 인계 완료 → 견적 승인 → 프로젝트 생성: 실제 Context 연결 성공.

- 반려 견적을 휴직 직원에게 재배정하여 재검토하면 거부, 적격 직원에게 재배정하면 성공.
- 직원의 진행 중 상담·미연결 승인 견적·미완료 프로젝트·미완료 작업 자격 검사는 `ERPContext.updateEmployee`에 있다. 완료 기록은 기존 담당자를 유지하는 예외가 있어 무조건 전 직원 자격을 현재 기준으로 강제하지 않는다.

### 상품 통합 테스트: 표시 형식 기대값 불일치

`src/10_product/ProductIntegration.test.js:30`은 기본 단가 input 값을 숫자 `14500`으로 기대한다. 현재 읽기 전용 표시 값은 `"14,500원"`이다. 별도 `audit.product-aligned.test.js`에서 표시 기대값을 바꾸면 기존 견적 데이터 불변 확인까지 통과한다.

이 두 실패를 새로운 상품/일정 기능 결함으로 계산하지 않았다. 두 복사본의 총 7개 테스트가 통과했지만, 원본 전체 테스트 실행 결과 자체는 **448/450**으로 유지하여 기록한다.

### 추가 테스트 작성 중 환경/시험 자료 수정

- CRA의 Jest 27이 Router 7의 `react-router/dom` export를 해결하지 못해 최초 추가 suite가 실행되지 않았다. 별도 실행 옵션으로 실제 배포 파일을 매핑하고 TextEncoder/TextDecoder polyfill을 추가했다. 앱 소스를 수정하지 않았다.
- 최초 직원 시험 입력의 필수 입사일 누락, Task 시험의 영업 직원 ID 사용, 상담 시험의 저장 키 오기는 시험 코드 오류였으므로 수정했다. 제품 결함으로 계산하지 않았다.
- 최종 47개 시험의 실패는 위 P2 5건이다. P1-01과 B-01은 ‘오류가 재현되는지’ 확인하는 테스트이므로 통과 목록에 포함된다.

## 9. 미검증·제한 사항

- 실제 브라우저 런타임/육안 레이아웃/반응형/키보드 접근성/Windows Chrome·Edge 차이.
- 실제 새로고침은 브라우저 실행 실패로 미실행. 저장 후 Provider 재마운트로 복원을 대체했다.
- 파일 선택, 이미지 디코딩/Canvas, 클레임 사진, 프로필 사진, 엑셀 실제 다운로드 결과.
- 외부 공휴일 API의 실제 통신/정확성. 테스트는 모의 응답 또는 실패 응답.
- 모든 검색어·필터·정렬·페이지 경계의 전수 조합. 고객/HR/홈페이지와 기존 상품·일정 검사 외에는 주로 정적 확인 및 렌더링이다.
- 전체 UI를 고객 등록부터 배송까지 단 한 번의 연속 클릭으로 모두 통과한 브라우저 E2E는 아님. Context 연속 흐름과 개별 실제 UI 이벤트 검사를 결합했다.
- 모든 역할별 모든 버튼, 게시판 답글·알림·프로필 변경의 전수 검사.
- 모든 모듈의 동시 탭·연속 빠른 클릭·저장소 용량 한계. 일정/상품의 기존 테스트가 다루는 범위와 B-01 오류 주입만 실행.
- UI 신규 기능 개발은 하지 않았다. 발견 사항의 수정 완료 여부도 이번 결과에 포함하지 않는다.

## 10. 발표 준비 관점의 최종 답변

### 11월 20일 발표 시연에 적합한가?

**조건부로 적합하다.** 현재 구조와 핵심 흐름은 4주 입문자 포트폴리오로 설명·시연할 수 있다. 다만 Task 목록 수정 오류를 고치거나 읽기 전용으로 정리한 뒤 실제 발표 PC에서 한 번의 전체 리허설을 통과시키는 조건이다. 테스트 수만 보고 완성됐다고 판단하지 않는다.

### 실제 사용 흐름에서 가장 위험한 기능은?

현재 가장 직접적인 위험은 **Task 목록의 상태·담당자 수정**이다. UI가 편집 가능해 보이지만 실제 동작은 예외가 난다. 상세 관리에서는 검증과 자동 완료가 작동하므로 경로를 혼동하면 시연 중 ‘같은 작업이 어떤 화면에서는 되고 다른 화면에서는 안 된다’는 상황이 된다.

그다음은 수량 입력 검증과 초기 할인 예시의 정책 불일치다. B-01은 정상 환경을 전제로 하는 이번 발표 준비의 최우선 문제로 확대하지 않는다.

### 남은 이틀 동안 반드시/우선 수정할 사항

1. **필수:** Task 목록의 세 변경 이벤트를 검증 API로 연결하거나 편집 UI 제거. 단순 `setTasks` 공개 금지.
2. **작은 수정 권장:** 소수 수량 거부, 견적 6번 seed 정책 일치, 초기화 시 홈페이지 마스터 모드 종료 또는 명시적인 종료 절차.
3. **가능하면:** 견적 상태 허용 목록 검증. 상담 FK 중앙 검증은 정상 자동 고객 생성과 함께 확인하며 수정한다.
4. **검수 유지:** 기존 테스트 2개의 기대값을 최신 정책/표시에 맞추되 앱 규칙을 테스트에 맞춰 약화하지 않는다.
5. **실제 발표 PC 리허설:** 깨끗한 초기화 → 로그인/비밀번호 변경 → 고객/상담/견적 → 프로젝트 → 네 Task 순차 완료 → 완료 잠금 → 재접속을 1회 이상 진행.

### 수정하지 않고 발표해도 무방한 사항

- 합의된 B-01 저장 실패 예외 처리 구조: 정상 저장소에서 리허설하고 일정상 보류 가능.
- 임의 Context 호출로만 확인한 상담 FK/견적 상태 검증: 정상 UI 시연 경로를 고정하면 후속 과제로 설명 가능. 다만 무결성이 완벽하다고 주장하지 않는다.
- 큰 리팩터링, 서비스용 인증/백엔드, 과거 데이터 마이그레이션.
- Task 접기 UI의 이번 제외 항목은 ‘정상’ 판정이 아니라 11월 18일 완성 후 확인 대상이다.

### 기능 개발을 중단하고 시연 준비에 집중해도 되는가?

**그렇다. 새 기능을 늘리기보다 P1 처리와 작은 정책 정리 후 기능을 동결하는 편이 좋다.** 검증된 Task 상세 화면을 중심으로 시연하고, 프로젝트 자동 상태·완료 이력·참조 삭제 제한·직원 인계를 대표 기능으로 설명하면 현재 구현의 강점이 드러난다. 최종 PC에서 아직 확인하지 않은 브라우저 동작을 검증하는 것이 지금 가장 가치 있는 다음 작업이다.
