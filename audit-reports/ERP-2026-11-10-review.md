## 해결된 항목

### A1. 프로젝트 등록 예외와 생산 빌드 실패 · 해결 반영

- **위치** `src/context/ERPContext.js:188–224`, `src/3_projects/ProjectForm.js:25–41,100–103`.
- **원인과 조치** 프로젝트 등록 함수가 선언되지 않은 `quotations`를 읽었습니다. 검증 복사본에서 현재 견적 훅의 `quotationData.quotations`를 조회하도록 바꿨습니다.
- **재검증** 생산 빌드가 성공했고 생성 번들이 JSDOM에서 프로젝트 목록을 렌더링했습니다. 기존 승인 견적과 신규 작성·승인 견적 양쪽으로 프로젝트를 등록했습니다. 등록 결과 복원, 사용한 견적의 선택 목록 제외, 미승인·미존재·납품일 누락·중복 견적의 저장 거절도 확인했습니다.
- **남은 빌드 경고** 복사본에서는 `ERPContext.js:1,3`의 미사용 `useState`, `initialQuotations` import 경고가 표시됐습니다.

## A. 남은 실제 오류

### A2. 임시 저장 견적 목록의 삭제 버튼이 작동하지 않음

- **위치** `src/2_quotation/QuotationList.js:8–10,161–168`, `src/context/useQuotationData.js:101–108`.
- **발생 조건과 확인** `/quotation`의 임시 저장 목록에서 삭제를 확인하면 `setQuotations is not a function` 오류가 발생합니다.
- **원인과 수정** 리스트는 Provider에 공개되지 않은 setter를 호출합니다. 이미 제공되는 `deleteQuotation(q.id)`를 사용하고, A3의 참조 제한과 실패 안내도 같은 삭제 함수로 통일하세요.

### A3. 참조 중인 고객·견적을 삭제하면 프로젝트와 견적에 끊어진 참조가 남음

- **위치** 고객 `src/1_crm/02_CustomerManagement.js:79–95`, `src/context/useCustomerData.js:59–65`. 견적 `src/2_quotation/QuotationDetail.js:96–105,253–259`, `src/context/useQuotationData.js:83–88`. 표시 영향 `src/3_projects/ProjectDetail.js:37–49`, `src/3_projects/ProjectQuotationInfo.js:4–6`.
- **발생 조건과 확인** 초기 프로젝트 1이 가리키는 견적 1을 상세 화면에서 삭제하면 프로젝트의 `quotationId`는 그대로 남습니다. 고객 1 삭제도 실제 Context에서 수행했으며 기존 프로젝트와 견적의 `customerId`가 남았습니다. 연결 견적을 잃은 프로젝트 상세의 견적 영역은 숨겨집니다. **후속 재현**에서 고객을 먼저 삭제한 뒤 그 고객을 가리키는 승인 견적으로 신규 프로젝트를 등록할 수 있었습니다. 새 프로젝트에도 이미 삭제된 고객의 ID가 저장됐습니다.
- **원인과 수정** 고객·견적 삭제가 참조 검사 없이 자기 목록만 변경합니다. 팀에서 프로젝트에 적용한 삭제 제한과 맞추려면 Context에서 고객을 참조하는 상담·견적·프로젝트 및 견적을 참조하는 프로젝트를 확인하고 삭제를 거절하세요. 프로젝트 등록 시에도 선택 견적의 고객이 실제 존재하는지 확인해 이미 끊어진 데이터의 전파를 차단하세요. 화면은 결과의 성공 여부를 확인한 뒤 이동하거나 성공을 안내하세요.

### A4. 음수 수량과 납품일 없는 견적이 승인 대기로 저장됨

- **위치** `src/2_quotation/QuotationCreate.js:137–165,487–501,550–567,603–606`, `src/2_quotation/QuotationDetail.js:48–57`, `src/context/ERPContext.js:194–205`.
- **발생 조건과 확인** 유효한 견적의 수정 화면에서 수량을 음수로 입력하고 납품 예정일을 비운 뒤 저장하면 승인 대기로 들어갑니다. 승인 동작도 상태만 변경합니다. 납품일은 프로젝트 등록 검사가 요구하는 필드입니다.
- **원인과 수정** 승인 대기 저장 시 입력 문자열이 비어 있는지만 확인합니다. 견적 제출·승인 경로에서 양의 정수 수량, 팀 정책에 맞는 단가 범위, 실제 존재하는 납품일과 날짜 순서, 상품·담당자의 유효성을 공통 검사하세요. 임시 저장은 미입력을 허용할 수 있습니다.

### A5. 전체 초기화 후 독립 일정·게시글이 남고 기존 ID가 다시 쓰일 수 있음

- **위치** `src/components/Sidebar.js:8–15,66–73`, `src/context/ERPContext.js:302–315`, `src/5_schedule/scheduleStorage.js:51–55,159–165`, `src/6_dashboard/CommunityWritePage.js:24`.
- **발생 조건과 확인** 일정·게시글 저장값이 있는 상태에서 전체 초기화를 호출하면 ERP 훅과 로그인 세션은 초기화되지만 `made-mate-schedules`, `communityPosts`는 남았습니다. 일정 ID 연결과 게시글 작성자 ID의 재연결은 B2에 설명했습니다.
- **원인과 수정** 버튼이 모든 ERP 데이터 초기화를 안내하지만 실제 작업은 Provider 소유 훅에 한정됩니다. 전체 초기화 대상 키와 ID 카운터를 먼저 정하고, 대상 모듈의 화면 상태까지 갱신하세요. 일부만 초기화할 계획이면 버튼과 확인 문구에 적용 범위를 명시하세요.

### A6. 고객 저장값이 깨지면 ERP 앱 진입 자체가 중단됨

- **위치** `src/context/useCustomerData.js:8–13`, `src/context/ERPContext.js:20–30`.
- **발생 조건과 확인** `erp_customers`에 잘못된 JSON을 넣고 Provider를 마운트하면 `SyntaxError`가 발생합니다. 유효한 JSON이어도 배열이 아닌 값은 그대로 받아 후속 배열 처리에서 실패할 수 있습니다.
- **원인과 수정** Provider 초기화 경로에서 파싱 예외와 결과 형태를 검사하지 않습니다. 훅에서 예외와 레코드 형식을 검사하고, 상품·일정에서 쓰는 방식처럼 문제가 있는 원본을 보존한 뒤 복구 안내를 제공하세요.

### A7. CRM 수정 링크를 부모 창 없이 열면 렌더 오류

- **위치** `src/1_crm/01_CrmPage.js:17–21`, `src/1_crm/03_CustomerEdit.js:14–23,51`, `src/1_crm/03_CustomerRegister.js:53`.
- **발생 조건과 확인** `/crm/edit?id=1&popup=1`을 직접 열면 렌더 중 `TypeError`가 납니다. 등록 화면의 제출도 코드상 부모 창 함수에 의존합니다.
- **후속 검증** 정상적인 부모 창 함수를 제공한 JSDOM 테스트에서는 등록·수정과 재진입 후 저장 복원이 통과했습니다.
- **원인과 수정** 수정 화면은 `window.opener.getCurrentCustomers()`를 바로 호출합니다. 부모 창과 함수의 존재를 확인하고, 직접 접근은 Context 기반 화면이나 목록 복귀 안내로 처리하세요. 팝업 방식을 유지한다면 원본 고객이 삭제된 경우도 처리하세요.

### A8. 기본 앱 테스트가 실행되지 않고, 호환 설정을 보완해도 오래된 단언이 실패함

- **위치** `package.json:16–18,22`, `src/setupTests.js:1–5`, `src/App.test.js:1–8`.
- **발생 조건과 확인** 원본 `npm test`에서 앱 테스트가 `Cannot find module 'react-router/dom'`으로 중단됩니다. 검수용 설정에 Router DOM의 CommonJS 매핑과 TextEncoder/TextDecoder를 추가하니 App이 렌더됐지만, 테스트가 대시보드에 없는 `learn react` 링크를 찾다가 실패했습니다.
- **원인과 수정** 현재 CRA/Jest 설정이 설치된 Router의 하위 경로를 해석하지 못하며, 앱 테스트는 CRA 초기 템플릿입니다. 팀의 테스트 설정에서 Router를 정식으로 해석하게 하고 대시보드나 라우트의 실제 요소를 검증하세요.

## 2. 이미 올바르게 구현된 동작

- **상담에서 프로젝트까지**. 신규 상담을 견적 요청으로 저장하면 고객이 생성되고, 견적에서 그 고객을 선택할 수 있습니다. 상품의 기본 단가가 견적에 들어가고, 승인 이후 프로젝트를 만들면 견적의 고객과 납품일을 가져옵니다. 신규·기존 승인 견적 양쪽의 프로젝트 등록을 확인했습니다.
- **첫 로그인과 게시판**. 계정 발급 화면에서 만든 계정은 첫 로그인 시 강제 비밀번호 변경 화면을 엽니다. 확인 입력이 다르면 변경을 막고, 변경 후에는 기존 비밀번호를 거절합니다. 일반 직원의 공지 작성 차단, 매니저의 일반 공지 작성, 관리자의 중요 공지 작성, 커뮤니티 작성자 ID 저장을 확인했습니다.
- **프로젝트와 HR의 연결 보호**. 프로젝트의 고객·견적 변경을 거절하고 작업 마감일이 범위를 벗어나는 기간 수정도 막습니다. 미완료 담당 프로젝트가 있으면 휴직을 막고, 적합한 담당자로 바꾸면 휴직을 허용합니다. 참조 중인 직원을 삭제할 수 없습니다. 작업이 없는 프로젝트의 삭제와 변경 이력 정리, 작업이 있는 프로젝트의 삭제 제한을 확인했습니다.
- **작업 검증과 단계 필터**. 필수 항목, 프로젝트 존재 여부, 담당 부서·재직 상태, 마감일 범위, 동일 프로젝트 내 단계 중복을 검사합니다. 목록의 `statusFilter`가 실제로 `taskStatus`로 필터링함을 렌더 테스트로 확인했습니다. 초기 작업 12건에는 배송 관리가 없어 초기 데이터에서 배송을 선택하면 빈 결과가 정상입니다.
- **직원 입력**. 이메일 대소문자를 무시해 중복을 막으며, 잘못된 연락처와 존재하지 않는 입사일을 거절합니다. 신규·수정·미참조 직원 삭제와 재마운트 후 복원을 확인했습니다.
- **계정·인증**. 중복 발급과 잘못된 역할, 마지막 활성 관리자 강등·비활성화, 잘못된 비밀번호와 새 비밀번호 불일치를 막습니다. 활성 계정으로 휴직 중 로그인할 수 있고, 퇴사 시 계정 비활성화 및 현재 탭의 로그아웃, 퇴사 직원 계정 재활성화 제한이 작동합니다. 이메일 앞뒤 공백과 대소문자 정규화, 세션 복원, 초기화 로그아웃을 확인했습니다.
- **초기 데이터**. 프로젝트 5, 직원 23, 견적 10, 작업 12, 고객 50, 상담 20, 상품 10, 계정 5건을 확인했습니다. 프로젝트-견적 고객 일치, 프로젝트·작업 담당 자격, 연결된 상담의 고객 존재, 견적의 고객·상품·직원 존재, 계정의 직원 존재 검사에서 불일치가 없었습니다.
- **상품·일정**. 기존 테스트에서 상품 등록·수정·판매 상태·이미지·CSV·재진입·저장 오류, 일정의 등록·수정·삭제·프로젝트 연결·저장 오류 및 탭 충돌 관련 동작을 확인했습니다. 실행한 테스트는 JSDOM 기반입니다.
