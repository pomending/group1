## 1. 검수 요약

### 1.1 전체 안정성 및 발표 시연 판단

**정상 입력을 사용하는 핵심 업무 시연은 조건부 가능하다.** 프로덕션 빌드가 성공했고, 실제 React ERPProvider와 각 Hook을 연결한 실행 테스트에서 상담 접수 → 고객 연결·견적 요청 → 견적 생성·상담 인계 완료 → 승인 완료 → 프로젝트 생성 → 제작·검수·포장 완료 → 배송 완료 → 프로젝트 자동 완료·변경 이력 생성이 이어졌다.

직원·고객 참조 삭제 방지, 반려 견적 담당자 재배정, 프로젝트 중복 생성 방지, 작업 단계 중복 방지, 프로젝트 기간 보호, 완료 후 프로젝트/작업 잠금은 주요 실행 사례에서 정상 동작했다. 최근 변경사항을 단순히 미구현으로 분류할 상황은 아니다.

다만 **마이페이지 비밀번호 변경은 실제 화면 이벤트에서 실패를 성공으로 표시**했다. 전체 초기화도 정상 저장소에서는 작동하지만 저장 실패 시 성공을 반환하거나 예외를 밖으로 던지는 경로가 있다. 이 두 항목을 우선 수정하고, 실제 발표 PC에서 화면 리허설을 마쳐야 한다.

실제 Chromium 실행은 환경 제한으로 완료하지 못했다. 아래의 “DOM 실행”은 React Testing Library + jsdom 검증이며, 실제 브라우저의 레이아웃·마우스 hit testing·이미지 표시를 확인한 것은 아니다.

### A-01. 마이페이지 비밀번호 변경 실패가 성공으로 표시됨 — P1

- **위치:** `src/6_dashboard/MyPage.js:159–174`, 특히 **170행**. 반환 계약은 `src/context/useAccountData.js:184–217`.
- **발생 조건:** 마이페이지에서 현재 비밀번호를 틀리게 입력하거나 새 비밀번호가 Hook의 검증을 통과하지 못함. 입력란을 모두 채우고 새 비밀번호 두 칸을 일치시키면 화면 선행 검사를 통과한다.
- **실제 동작:** “비밀번호가 변경되었습니다.” 안내, 변경 창 닫힘. 실제 계정 비밀번호는 기존 값 유지.
- **재현:** 초기 관리자 계정으로 로그인 후 마이페이지 비밀번호 변경에서 현재 비밀번호 `wrong1234`, 새 비밀번호/확인 `newpass1234` 입력 → 변경 실행. 실제 DOM 이벤트 테스트에서는 Enter로 실행했다.
- **원인:** `changePassword()`는 `{ok:false,message:...}`를 반환한다. `if (!changePassword(...))`는 객체 전체를 검사하므로 실패 객체도 truthy로 취급되어 실패 분기로 가지 않는다.
- **영향:** 사용자에게 잘못된 비밀번호를 기억하게 만들며 이후 로그인 시연이 실패할 수 있다. 비밀번호 검증 자체가 우회되어 저장되는 문제는 아니다.
- **권장:** 결과를 변수에 받고 `if (!result.ok)`에서 `result.message` 표시 및 입력 유지. 성공일 때만 창 닫기. `ChangePasswordPage.js:16`의 기존 처리 패턴과 맞추면 된다.
- **실제 테스트:** **DOM 재현 완료.** 성공 문구 출력과 계정 비밀번호 미변경을 함께 확인했다.

### A-02. 새 일정이 숫자 PK 전제와 달리 문자열 ID로 저장됨 — P2

- **위치:** `src/5_schedule/ScheduleManager.js:51–52`, `:560–574`, 회차 분리 `:615`.
- **발생 조건:** 신규 일정 생성 또는 반복 일정의 한 회차를 분리하여 저장.
- **실제/예상 동작:** `schedule-<timestamp>-<random>` 문자열이 `item.id`에 들어간다. 회차 연결의 `replacesScheduleId`도 이 ID를 참조한다.
- **재현:** 새 일정을 저장하고 `made-mate-schedules`의 새 항목 `id` 타입 확인. 이번 실행에서는 원본의 ID 생성 표현식을 추출해 실행하여 반환 타입 `string`을 확인했고, 그 값을 저장 객체에 넣는 경로를 정적 추적했다. 새 일정 UI 저장 전체를 추가 실행한 것은 아니다.
- **원인:** 일정 모듈이 독자적인 문자열 ID 발급 규칙을 유지한다.
- **영향:** “모든 PK/FK 숫자”라는 이번 검수 전제를 현재 신규 데이터가 만족하지 않는다. 일정 코드는 이 형식으로 동작하도록 작성되어 있으므로, 문자열이라는 이유만으로 현재 달력이 깨진다고 판단하지 않는다. 향후 숫자 전제의 공통 검증/API 연계에서 충돌할 수 있다.
- **권장:** 팀 규칙을 적용하려면 신규 영속 일정 ID와 자기 참조를 숫자 ID로 통일하고 관련 테스트를 갱신한다. 일정 PK만 예외로 둘 계획이라면 스키마 규칙에 명시해야 한다. 지금처럼 전제와 구현을 다르게 두지 않는다.
- **실제 테스트:** **생성 함수 타입 실행 + 저장 경로 정적 확인.** 과거 데이터 호환성 문제로 분류한 것이 아니다.
- **제외:** `project-1-start`, `task-deadline-1` 같은 달력 표시 전용 파생 ID는 저장 엔티티 PK와 달라 이 항목에 포함하지 않았다. 이미지 파일명의 문자열 ID도 같은 오류로 세지 않았다.

### B-01. 전체 초기화가 일부 실패를 성공으로 처리하거나 예외를 반환 밖으로 던짐 — P1

- **위치:** `src/context/ERPContext.js:1426–1447`, 특히 **1437행**. `src/context/useProductData.js:108–117,170–171`; `src/6_dashboard/dashboardStorage.js:4–20`; `src/components/Sidebar.js:16–23`.
- **발생 조건:** 초기화 중 상품 저장소 쓰기 실패 또는 대시보드 키 삭제 실패 등 저장소 예외.
- **실제 동작 1:** `resetProducts()`가 `{ok:false}`를 반환해도 무시하고 나머지 초기화를 진행, 로그아웃 후 `{ok:true}` 반환. 상품은 변경 전 상태가 남을 수 있다.
- **실제 동작 2:** `communityPosts` 삭제가 예외를 던지면 `resetAllData`가 `{ok:false,message}`를 반환하지 못한다. 그 전에 일부 다른 모듈은 이미 초기화될 수 있다.
- **재현:** ① 상품 가격 수정 ② `Storage.setItem` 중 `erp_products`만 예외가 나게 하는 fault injection ③ resetAllData 실행 → 성공 반환인데 상품 가격이 수정값으로 유지. 별도로 `removeItem('communityPosts')`에 예외 주입 → reset 호출에서 예외 발생.
- **원인:** 일정 reset 반환만 검사하고 각 Hook의 실패 계약을 통합하지 않았다. 정상 상태 변경과 localStorage effect 저장을 하나의 성공 결과로 다루고 있다.
- **영향:** 초기 데이터 간 불일치, 초기화 완료 오인. 사진/게시판 데이터가 남아 새로 사용되는 직원 ID와 연결될 위험. 정상 저장소에서 늘 발생하는 오류는 아니다.
- **권장:** 반환값이 있는 초기화 함수는 반드시 결과를 검사하고 예외를 `{ok:false,message}`로 변환한다. 실패가 발생하기 전에 변경된 데이터가 있으면 “부분 초기화” 사실을 알려야 한다. 프론트엔드 시연 범위에서는 최소한 거짓 성공을 막고 실패 후 상태를 명확히 표시한다. 단순 try/catch만으로 여러 useEffect 저장의 원자성이 보장되는 것은 아니다.
- **실제 테스트:** **두 종류 fault injection 재현 완료.** 정상 초기화 및 Sidebar 이동 테스트는 성공했으므로 정상 경로까지 실패로 분류하지 않았다.

### B-03. 고객 최종 데이터 검증이 공통 저장 경로에서 일관되지 않음 — P2

- **위치:** `src/context/ERPContext.js:143–167,170–206`; `src/context/useCustomerData.js:25–62`; `src/9_consultation/02_ConsultationManagement.js:55–75,110–123,145–163`; `src/utils/consultationUtils.js:43–48`.

- **UI 분석:** CRM Register/Edit에는 필수값·전화·이메일·사업자번호·메모 검증이 있고, 상담 입력에도 필수값·전화·이메일 검증이 있다. **상담 경로에 검증이 전혀 없다는 지적은 틀리다.** 차이는 최종 저장할 고객 객체를 검증하지 않는 점이다.
- **특정 경로:** 상담의 원래 메모 1,000자는 `validateMemo(editData.memo)`를 통과하지만 새 고객 메모는 날짜와 ` | `가 붙어 1,013자가 된다. 기존 고객 메모에 추가하면 더 길어질 수 있다. 이후 CRM에서 그 고객을 저장할 때 1,000자 제한에 걸릴 수 있다. 이 길이 변환 경로는 정적 분석이며 상담 UI에서 긴 문장을 입력해 전 과정을 재현하지는 않았다.
- **재현:** 공통 API에 `{employeeId:유효영업직원,companyName:'',customerManager:'',phone:'',email:'invalid'}` 전달 → 저장 성공. 실제 실행했다. 메모 경로는 1,000자 상담 메모를 견적 요청 상태로 저장한 후 고객 편집에서 확인하면 된다.
- **원인:** 화면마다 검사하고 Context는 담당자 검사만 수행한다. 상담에서 변환한 고객 데이터와 CRM의 고객 입력 제약이 일치하지 않는다.
- **영향:** 추가 기능이나 다른 호출 경로가 잘못된 고객 데이터를 저장할 수 있고, 상담 생성 고객을 CRM에서 수정할 때 예상치 못한 거부가 발생할 수 있다.
- **권장:** 최종 고객 데이터에 적용하는 순수 검증 함수를 공통화하고 add/save 양쪽에서 호출한다. 누적 메모의 길이 정책은 일반 입력 길이와 구분하거나 일관되게 적용한다. 화면 alert는 유지하되 데이터 검증은 반환값 기반으로 통합한다.
- **실제 테스트:** **공통 API의 잘못된 필수값 저장 재현 완료 / 누적 메모 영향은 정적 확인.** 정상 CRM 모달 검증은 통과한 별도 결과로 유지한다.

## 4. 모듈별 검수 결과

### 4.1 구조·라우팅·Context

- `App.js`의 BrowserRouter 안에 단일 ERPProvider가 있고, 내부 ERPContent가 로그인/외부 홈페이지/ERP 화면을 분기한다. 고객 모달은 이 Provider의 자식이므로 별도 창 상태 동기화에 의존하지 않는다.
- 모듈: `1_crm`, `2_quotation`, `3_projects`, `4_tasks`, `5_schedule`, `6_dashboard`, `7_login`, `8_hr`, `9_consultation`, `10_product`, `11_homepage`; 공통 `context`, `utils`, `data`, `components`.
- `/homepage`는 로그인 제한 전에 외부 레이아웃으로 표시한다. 일반 ERP 경로는 currentUser 없으면 `/login`으로 이동한다.
- `/hr/accounts`에는 ADMIN route 조건이 있다. 다른 모든 업무의 직원/관리자별 세부 권한 차이를 이번 요청에서 새로 요구한 것으로 해석하지 않았다.
- 대시보드의 커뮤니티·공지·마이페이지는 `/?page=...` 분기로 렌더링된다. 별도 `/mypage` route가 없다고 누락 처리하지 않았다.
- Context가 Hook의 데이터 및 함수를 모은 뒤 교차 참조 검증 함수를 덮어써 공개한다. 개별 reset 일부를 숨기고 resetAllData만 공개하는 것은 의도된 참조 보호 구조다.
- 충돌 마커 `<<<<<<<`, `>>>>>>>`는 JS에서 발견하지 못했다. 현재 빌드가 성공했으므로 import/JSX의 치명적 병합 파손 증거는 없다. Git 이력이 없는 ZIP이므로 특정 팀원의 커밋 보존 여부는 확인할 수 없다.

### 4.2 CRUD 인자·반환값

| 경로 | 현재 계약 | 판단 |
|---|---|---|
| 프로젝트/작업/견적 | 객체 입력·`{ok,message?}` | 화면 및 Context 주요 사용처와 일치 |
| 고객 Hook add | 숫자 newId | Context가 `{ok:true,id}`로 감싸 공개하므로 오류 아님 |
| 고객 Hook edit | void | Context가 유효성/존재 확인 후 `{ok:true}` 공개 |
| 상품 add/update | `{ok,product?,field?,message?}` | 현재 updateProduct는 **객체 하나**를 받음 |
| 계정 생성/권한/상태 | boolean | AccountManagement의 호출 방식과 함께 봐야 함 |
| 비밀번호 변경 | `{ok,message?}` | MyPage만 boolean으로 오인: A-01 |
| 전체 초기화 | 정상 `{ok:true}` | 실패 계약 불완전: B-01 |

모든 함수를 일괄적으로 같은 반환 형태로 바꿀 필요는 없다. 발표 전에는 실제 계약 불일치가 있는 호출처를 우선 수정하는 편이 안전하다.

### 4.3 데이터 객체·PK/FK

- 초기 업무 데이터에서 검사한 고객/상담/견적/프로젝트/작업/직원 PK는 숫자이고 중복이 없었다.
- 프로젝트→견적/고객/관리자, 작업→프로젝트/직원, 고객→직원, 상담→고객/직원(nullable), 견적→고객/직원 참조는 초기 fixture에서 유효했다.
- 초기 5개 프로젝트의 고객과 납품일은 연결 견적과 일치했다. 초기 12개 작업은 프로젝트 기간 안에 있었다.
- 초기 상품은 별도 productData 생성 경로도 사용하므로 단순 mockData 한 파일만 보고 전체 저장 경로를 단정하지 않았다.
- 현재 신규 일정의 영속 PK는 숫자가 아니다(A-02). 예전 데이터 호환성 문제가 아니라 현재 생성 정책이다.
- 견적과 상담은 `consultationId` 영속 FK가 없이 생성 함수의 인자로 인계를 수행한다. 소스 주석에도 명시되어 있다. 따라서 특정 견적 삭제로 특정 상담을 자동 되돌려야 한다는 기능은 이번 요구에 없으며 임의로 오류 처리하지 않았다. 1:1 추적 기능을 추가할 때는 별도 설계가 필요하다.

### 4.4 로그인·계정·직원

- 이메일 비교는 trim/lowercase 처리; 계정 활성·비밀번호·직원 퇴사 여부 검사.
- 휴직 직원 로그인은 허용되는 현재 정책이다. 신규 계정 발급은 재직만 허용하는 코드다. 두 조건을 같은 의미로 혼동하지 않았다.
- 계정 비활성화 시 currentUser가 사라지고 logout effect가 sessionStorage를 제거한다.
- 일반 퇴사 변경 경로에서 계정도 비활성화하므로 App의 Boolean(currentUser)만 보고 “정상 퇴사 경로에서 계속 로그인 유지”로 단정하지 않았다.
- 초기 `mustChangePassword:true` 계정은 ChangePasswordPage로 유도된다. 마이페이지의 A-01과 초기 비밀번호 변경 페이지의 정상 result.ok 처리를 구분했다.
- 서버 없이 localStorage에 시연 계정을 저장하는 구조 자체는 이번 범위의 결함으로 세지 않았다.

### 4.5 고객·상담·견적

- CRM 등록/수정 실패 및 성공 반환값 처리가 존재한다. 모달이 닫히기 전에 성공 여부를 검사한다.
- 상담에서 기존 고객은 회사명 일치로 찾아 연결하며 필요한 연락처/메모를 갱신한다. 사업자번호를 기준으로 회사를 식별하는 설계는 아니다. 동명 회사 구분은 정책 선택 사항으로 남긴다.
- 상담 `견적 요청`/`인계 완료`의 고객·상태 변경 제한이 Hook에 존재한다. 견적 정식 등록 후 인계 완료로 바뀐다.
- 반려 견적의 재검토는 직원 ID와 상태를 한 번의 updateQuotation에 넣고, 유효한 기존 직원은 유지한다. 변경 후 활성 견적으로서 담당 자격을 Context에서 다시 확인한다.
- 견적 Detail의 프로젝트 연결 견적 재검토 버튼이 노출될 수 있지만 저장 경로는 거부한다. 사용자에게 제한 사유를 일찍 표시하는 개선은 가능하나 보호 기능 누락으로 세지 않았다.
- 상품 0원 등록 허용과 정식 견적의 최종 단가 양수 정책은 서로 다르다. 0원 상품을 실제 견적에 사용할 계획이라면 팀 정책을 정해야 하지만, 이번 검수에서는 새로운 판매 정책을 가정해 결함 수를 늘리지 않았다.

### 4.6 프로젝트·작업·일정

- 프로젝트 담당은 재직 경영지원팀, 제작/검수/포장은 재직 생산팀, 배송은 재직 물류팀을 사용한다. 예전 부서명 설명보다 현재 코드/데이터를 기준으로 확인했다.
- 프로젝트 진행률은 완료된 서로 다른 작업 단계 수를 4단계로 나누는 방식이다.
- 배송 작업을 처음 생성하면서 완료시키는 경로도 차단한다. 일반 updateProject로 수동 완료시키는 경로도 차단한다.
- 완료된 작업 담당자가 퇴사했어도 완료 기록을 그대로 유지할 때는 기존 담당자 보존을 허용한다. 미완료로 되돌리면 자격 검사를 다시 받는다.
- 일정은 프로젝트 시작/마감과 작업 마감 파생 항목을 별도로 생성한다(`ScheduleProjectBridge.js:126` 이후, `:166` 이후). 이 파생 항목을 영속 업무 PK와 동일하게 해석하지 않았다.
- 일정 저장은 debounce/원격값 비교/resetId/초기화 이벤트를 사용한다. 기존 일정 suite 및 저장소·bridge·validation 테스트는 통과했다.
- 프로젝트 삭제 시 연결 일정 정리, 직원 삭제 시 담당/참석자 일정 정리가 Context에서 호출된다. 모든 반복 회차와 삭제 undo의 조합을 추가 수동 실행한 것은 아니다.

### 4.7 홈페이지·상품·클레임

- HomeProduct는 `useERP().products`를 사용하고 `productStatus === '판매 중'`으로 공개 목록을 제한한다. 외부 홈페이지가 별도 하드코딩 상품 배열만 보여 준다는 문제는 없다.
- 클레임 등록은 표시 주문번호를 상담 ID로 파싱하고, 존재하는 `인계 완료` 상담 및 업체명 일치를 Context에서 검사한다.
- 내부 상담 화면은 claims에서 접수/처리 중 항목을 조회한다. 홈페이지와 ERP의 claim 데이터 소스는 연결되어 있다.
- 홈페이지 master는 ERP 로그인과 별도 sessionStorage 플래그 및 시연용 번호로 운영된다. ERP route 자체는 여전히 로그인 gate를 통과해야 한다. 이를 실제 서비스 인증으로 평가하지 않았다.
- `homepage_master`는 resetAllData/logout에서 제거하지 않는다. 이번 명시적 대시보드 기록 제거 목록에는 없으므로 별도 오류로 세지 않았지만, 외부 고객 화면을 “비관리자 상태”로 시연할 때는 홈페이지의 마스터 종료를 사용해야 한다.
- 사진 첨부와 클레임 입력·등록·관리자 상태 변경의 전체 UI 시나리오는 추가 브라우저 테스트를 완료하지 못했다.

### 4.8 대시보드·게시판·사진·알림·저장소

- DashboardPage는 게시글을 localStorage에서 초기 로드하고 작성/수정/삭제 핸들러가 저장한다. 게시글 배열 전체를 자동 재저장하는 effect가 없어 초기화 직후 이전 게시판 state가 자동으로 복구되는 구조는 발견하지 못했다.
- 실제 App DOM에서 대시보드 상태와 이전 저장 키를 만든 뒤 Sidebar 초기화 → 로그인 route → 이전 키 제거를 확인했다.
- Topbar는 직원 ID로 사진·알림을 읽는다. 직원 이름 변경 시 effect가 갱신된다. 새 마감 알림은 초기화 후 mock 업무로부터 다시 만들어질 수 있는데, 이것은 이전 기록 잔존과 구분해야 한다.
- 프로필 사진은 256×256 캔버스로 변환 후 직원 ID별 저장한다. 실제 이미지 품질·브라우저 canvas 동작은 미확인이다.
- 각 Hook의 저장 오류 처리 수준은 다르다. 직원/상품에는 일부 catch/오류 상태가 있고, 다수 Hook은 effect 저장 예외를 직접 처리하지 않는다. 전체 초기화의 실패 오인 문제는 B-01에 묶었으며 같은 위험을 모듈별 중복 집계하지 않았다.

## 6. 실행하지 못했거나 확인할 수 없는 사항

1. **실제 브라우저 UI 검증:** Playwright 관리 Chromium이 없어 다운로드를 시도했으나 정상 압축 파일을 받지 못했다. 시스템 `/usr/bin/chromium`도 `socket() failed: Operation not permitted`로 종료됐다. 따라서 실제 마우스 배경 차단, viewport별 화면 겹침, 키보드 focus 이동, 스크롤, 시각적 CSS 충돌은 검증 완료가 아니다.
2. **전체 업무 흐름의 화면 클릭 E2E:** 상담부터 배송까지 실제 Context 함수로 실행했지만 모든 단계를 실제 브라우저에서 클릭하지 않았다. 상담 화면의 모든 필드·견적 상세 재배정 select를 사용한 전체 E2E는 미실행이다.
3. **사진·파일 기능:** 실제 프로필 사진 파일 선택/캔버스, 클레임 사진, 상품 이미지 업로드/브라우저 렌더링, 고객 엑셀 다운로드 결과 파일의 내용은 추가 end-to-end 검증을 하지 않았다. 기존 상품 테스트 통과와 실제 이미지 브라우저 확인은 구별한다.
4. **전체 조합:** 모든 직원 상태×부서×업무 상태 조합, 모든 일정 반복 규칙×삭제 복원×초기화 조합, 각 모듈 화면에서의 초기화와 저장 중 실패를 전수 실행하지 않았다.
5. **저장 실패 후 복구:** 실패 주입으로 B-01은 재현했으나 사용자의 실제 브라우저 저장 한도 도달을 유발한 것은 아니다. 초기화 중 모든 저장 키의 실패 순열이나 롤백 보장은 검증하지 않았다.
6. **여러 탭·여러 사용자:** 일정/상품에 관련 방어 코드와 기존 테스트가 있지만 이번 검수에서 전 ERP를 여러 실제 브라우저로 동시에 조작하지 않았다. 요청 범위를 넘는 서버 수준 동시성 문제는 결함으로 나열하지 않았다.
7. **Git 병합 이력:** 첨부는 소스 ZIP이므로 실제 master 부모 커밋, 충돌 해결 과정, 팀원별 모든 변경 보존 여부는 확인 불가다. 현재 코드 동작과 잔여 충돌 마커 기준으로 판단했다.
8. **이전 보고서 비교:** 이번 요청에 이전 보고서가 첨부되지 않았으므로 과거 항목 번호를 임의로 매칭하지 않았다.
9. **호환성·시연 PC:** Windows Chrome/Edge, 모바일, 자정 경계, 시간대 차이, 배포 서버 직접 URL 새로고침 처리는 미확인이다.
10. **예정 기능:** 2026-11-17 예정인 “승인 완료이지만 아직 프로젝트가 없는 견적 수 표시”는 이번 오류/누락 항목에서 제외했다.
